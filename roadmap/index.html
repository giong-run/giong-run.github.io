1.0Stable3 itemsA stable API.

A stable API. No features are added between 0.6 and 1.0; what is left is a series of gates (0.6, 0.7, 0.8, 0.9), and 1.0.0 follows release candidates (1.0.0-rc.N) that pass them all.

  • Documentation: every public item documented, and the limitations section of the README reduced to deliberate non-goals.
  • 0.8 and 0.9 passed.
  • 1.0.0-rc.N: release candidates that change nothing but fixes, until one passes every gate; that one becomes 1.0.0.

The API freeze also makes sure that nothing public ties the API to Linux or to HTTP/2 in a way that the releases below would have to break. A first pass over main found nothing that forces a 2.0, and a short list to settle before the freeze (findings).

After 1.0, each minor release has one main theme and breaks nothing: code written for 1.0 keeps compiling. The protocol and platform work runs on two tracks at once (a third, the runtime core, is described after 1.5), and each release ships as soon as its own gates pass. The protocol track does gRPC, which builds on HTTP/2, then HTTP/3, the largest piece of protocol work. The platform track first moves the system calls outside the drivers behind one internal layer, built once for both systems, then adds macOS, whose kqueue driver follows the path the epoll driver opened, then Windows, the largest change of platform. gRPC is 1.1 and macOS 1.2; HTTP/3 and Windows take 1.3 and 1.4 in the order they pass their gates. Nothing of 1.x lands on main before 1.0.0: until then only prototypes and measurements that touch no released code, and 1.0.x fixes come from a release/1.0 branch afterwards. 1.5 follows on its own: it needs 1.2's overload protection and nothing from the others. WebSocket comes later, when someone needs it.

Every 1.x release keeps the Agent-first line (coded errors with their pages, one obvious way, llms.txt and AGENTS.md updated with the feature, giong-mcp and tracing for what it adds), passes a build of a small service by an AI agent from the documentation alone, and is benchmarked against the reference implementation named in its section before any claim about speed.

Two speed items once planned for 0.6 also wait until after 1.0, and land only with a benchmark showing what they buy: receive bundles (several buffers per completion) and optional NAPI busy polling. Two more for large machines, measured on a server with two sockets: workers that use the memory of their own NUMA node, and workers matched to the receive queues of the network card, so a packet is handled on the core it arrived on. giong already sizes and pins its workers by itself (CPU affinity and container quota) and spreads connections between them; it does not retune itself while running, which would make behaviour hard to predict, but giong-mcp suggests settings from what it measures.

1.1gRPC8 itemsgRPC on giong-http's HTTP/2 server and client, in a new crate, giong-grpc, on a protobuf of its own, and a simulation driver that tests every service deterministically.

gRPC on giong-http's HTTP/2 server and client, in a new crate, giong-grpc, on a protobuf of its own, and a simulation driver that tests every service deterministically.

  • Trailers in giong-http: a streamed response body that ends with trailers, and trailers that can be read at the end of a request body and of a client response. gRPC sends its status in them.
  • A client request body sent as it is produced, and a response that can be read while the request body is still being sent, for client-streaming and bidirectional calls. The server already keeps reading a request body while its answer streams; this milestone adds the test that holds it to that.
  • giong-grpc: unary, server-streaming, client-streaming and bidirectional calls; deadlines (grpc-timeout), status codes, metadata, cancellation, message size limits and gzip. Code generated from .proto files at build time, with no macros in user code and no protoc to install. Errors carry giong codes.
  • giong-proto: protobuf messages decoded as views over the receive buffer, with no copy and no allocation for strings and bytes, and encoded straight into the send buffer. Held to Google's protobuf conformance suite and fuzzed against prost.
  • The same service over gRPC-Web, for browsers, and as JSON over HTTP from the google.api.http annotations of its .proto: one definition, three ways to call it.
  • A simulation driver: a service, its clients and the network run in one thread, in simulated time, from a seed. Packets are lost, reordered and delayed, connections reset, disks fail and clocks jump as the seed decides, and a failing run replays exactly from its seed.
  • Health checking and server reflection, so standard tools (grpcurl, Kubernetes gRPC probes) work against a giong service.
  • Tested against grpc-go in both directions with gRPC's interoperability test cases, the message framing fuzzed, and benchmarked against tonic: calls per second, p99 latency and memory per open stream, for unary and streaming calls.

Done when: the interoperability test cases pass against grpc-go as client and as server, and a benchmark compares unary and streaming calls with tonic.

1.2macOS6 itemsgiong builds and runs on macOS, for developing and testing services on a Mac.

giong builds and runs on macOS, for developing and testing services on a Mac. Production stays on Linux. Two safeguards for code written in a hurry, on every system, ship with it.

  • A kqueue driver behind the same operations as io_uring and epoll: readiness like epoll, file operations on the pool of blocking threads, EVFILT_USER for wake-ups from other threads and EVFILT_SIGNAL for shutdown signals.
  • What macOS does differently: workers share one listening socket where SO_REUSEPORT does not spread connections, CPU pinning is skipped (macOS has no hard affinity), and sendfile and fallocate use their macOS counterparts.
  • Trust roots for giong-tls from the keychain, and DNS servers from the system configuration. Kernel TLS stays Linux only: Ktls::Auto keeps connections in the process.
  • CI on Apple Silicon: the test suite and the examples.
  • A worker guard: code that blocks a worker (a blocking call, a long loop) is reported while it happens, with where it was spawned and its stack, a coded error and the fix (spawn_blocking, or a yield in the loop).
  • Overload protection: an adaptive limit on requests in flight and load shedding with 503 and Retry-After before latency climbs, the path that 1.5's memory limit refuses work through, so a small server under a spike slows down gracefully instead of falling over.

Done when: the test suite passes on macOS in CI, and the examples run there unchanged.

1.3HTTP/35 itemsHTTP/3 (RFC 9114) over QUIC (RFC 9000) in giong-http's server and client, for the same handlers.

HTTP/3 (RFC 9114) over QUIC (RFC 9000) in giong-http's server and client, for the same handlers.

  • QUIC of its own, in a new crate, giong-quic, built for one core per connection: packets encrypted in place in the pool buffer, a whole flight sent with one segmentation-offload submission, connection IDs steered to their core, and no lock shared between workers. Crypto stays with rustls. Held to the QUIC interop runner against quinn, quiche, ngtcp2 and msquic, and fuzzed against quinn-proto. If it does not pass the core interop cases at a checkpoint about four weeks in, this release ships on quinn-proto behind the same API and the native engine follows in a later 1.x. Then TLS 1.3 through rustls's QUIC support (RFC 9001), loss recovery and congestion control (RFC 9002), connection migration, and 0-RTT off by default.
  • UDP for QUIC in giong::net: segmentation offload on send (GSO) and receive (GRO), ECN, the local address of each datagram, path MTU probing, and many datagrams per system call. A connection's packets reach the worker that owns it by connection ID, not by the sender's address, which changes when a client moves between networks.
  • HTTP/3 and QPACK (RFC 9204) in the server and the client, advertised with Alt-Svc, with the same limits and coded errors as HTTP/2. Frames, QPACK and packets fuzzed.
  • Automatic HTTPS: certificates from Let's Encrypt or any ACME server (RFC 8555, TLS-ALPN-01), renewed in the background, and one call that serves HTTP/1.1, HTTP/2 and HTTP/3 for a domain. Tested against Pebble, Let's Encrypt's test server.
  • Tested with h3spec, the QUIC interop runner and browsers (Chromium and Firefox in CI), with packet loss and reordering injected; benchmarked on bare metal against HTTP/2 on giong and against quinn with h3 on Tokio.

Done when: browsers load pages from a giong server over HTTP/3, the interop runner's core test cases pass, and the bare-metal benchmark is published with its method.

1.4Windows6 itemsgiong builds and runs on Windows, for services that have to run there.

giong builds and runs on Windows, for services that have to run there. Linux stays the platform it is tuned for.

  • An IOCP driver. I/O completion ports complete operations the way io_uring does, so buffers handed over and handed back fit as they are: AcceptEx, ConnectEx, WSARecv, WSASend, TransmitFile and overlapped file I/O, with CancelIoEx and each buffer kept until the kernel has let go of it. A zero-byte receive keeps idle connections from holding a pool buffer each.
  • What Windows does differently: no Unix domain sockets or file modes at first, workers share one listening socket instead of SO_REUSEPORT, Ctrl+C, Ctrl+Break and closing the console stop the runtime, and CPU pinning goes through processor groups.
  • Trust roots for giong-tls from the Windows certificate store, and DNS servers from the network adapters.
  • CI on Windows: the test suite and the examples. Speed measured against Tokio on the same Windows machine, and published as it comes out. Tokio emulates readiness on top of I/O completion ports; a driver that uses completions directly does not have to.
  • Registered I/O (RIO), Windows' registered-buffer interface, closest to io_uring, where a benchmark shows it beats plain completion ports.
  • giong-mcp answers "why is this slow, why is it stuck" on every system: the slowest places tasks are spawned from, blocked workers, pools waiting, shed requests, in one report an agent can act on.

Done when: the test suite passes on Windows in CI, and a benchmark against Tokio on Windows is published with its method.

1.5Lean under pressure5 itemsHardware, memory above all, is expensive, so a service should carry heavy load on a small machine and never fall over for lack of memory. giong already spends 5 to 10 times less memory per idle connection than Tokio and Go (see the README); what no Rust runtime offers is a memory limit it keeps whatever clients do.

Hardware, memory above all, is expensive, so a service should carry heavy load on a small machine and never fall over for lack of memory. giong already spends 5 to 10 times less memory per idle connection than Tokio and Go (see the README); what no Rust runtime offers is a memory limit it keeps whatever clients do. Like the releases above, this one breaks nothing: everything is opt-in, and code written for 1.0 behaves as before. It stays a runtime feature: the limit and its ledger live in giong, and the protocol crates charge what they hold to it.

  • A memory limit for the whole process (Builder::memory_limit, or read from the container's cgroup), kept by one ledger per worker with no lock: buffers, request bodies, HTTP/2 and TLS state, queued messages, tasks, and the kernel's socket memory, which a container's limit counts too. As memory runs short giong gives back what it can spare first, then slows clients down by not reading from them, then refuses new work (503 with Retry-After, REFUSED_STREAM), and only last cuts the one request holding the most memory, with a coded error naming it. It never aborts.
  • Memory charged to the request that holds it: a declared estimate per request, and an optional counting global allocator that wraps the system's or another (jemalloc, mimalloc), so the limit covers the application's allocations too. giong-mcp shows what holds memory, by connection and request.
  • Accounts per tenant in the ledger, under a key the service chooses, so one tenant over its quota of memory or requests in flight is refused while the others are served. The runtime keeps the accounts; which key to use (a client address, a header, a TLS identity) is decided in giong-web, with the rate limiting planned for 1.x.
  • Idle connections as small as the kernel's share of them or smaller, where it is not done before: an idle HTTPS connection under 4.5 KiB (12.5 KiB in 0.7; nginx with OpenSSL 15), an idle HTTP/2 connection under 3 KiB (4.5), and HTTP/2 requests with at most 4 heap allocations each (22).
  • Proven under attack: slow uploads, slow heads, slow readers, floods of HTTP/2 streams and of new connections, handlers that allocate more than they declared, alone and mixed, in containers of 64, 128 and 256 MiB, in CI, under the simulation driver and on bare metal.

Done when: no out-of-memory kill in any case of the attack matrix, well-behaved clients mixed into it keep at least 90% of their requests per second, the limit costs at most 1% more instructions per request, and the cheapest-machine benchmark of 0.9 is published again with the limit on, against Tokio, Go and nginx.

1.xRuntime core (track R, after 1.0)9 itemsWhat a general runtime still lacks, from a gap analysis of the core against Tokio, Seastar, glommio, monoio, Go and Erlang.

What a general runtime still lacks, from a gap analysis of the core against Tokio, Seastar, glommio, monoio, Go and Erlang. This track runs beside the protocol and platform tracks; each item ships in the first 1.x release whose gates it passes, breaks nothing, and lands only with its tests under the simulation driver, a coded error and page for every new failure, and a benchmark with raw data for any claim about speed or memory. Like the rest of 1.x, it stays on branches until 1.0.0.

First wave, needing nothing else:

  • Blocking and compute work: spawn_blocking on a bounded pool, and a compute pool sized from the same CPU budget as the workers (the container's quota), with a bounded queue, so a blocking call or a CPU-heavy job never stalls a worker.
  • Processes and signals: child processes waited for through the ring (waitid, or a pidfd), their standard input and output as streams, the process's own stdin and stdout, pipes, any signal as a stream, Unix datagram sockets, passing descriptors between processes, and listeners taken from systemd.
  • Structured concurrency: scopes whose child tasks never outlive them, task groups, values local to a task, and a deadline per scope that the kernel enforces on every operation inside it (a linked timeout in io_uring, the timer wheel on epoll), with the reason for a cancellation as a coded error.
  • Work done inside the kernel: splice between sockets, wake-ups and descriptors sent between workers' rings (MSG_RING), registered buffers, receive bundles.

Second wave, after the first:

  • Scheduling groups: shares of CPU and of disk I/O per class of work (requests, background jobs, tenants), so background work does not raise request latency. Needs the scopes.
  • Restarts that drop nothing: the new process takes the listeners from the old one, which drains; later, idle connections are handed over too, kernel TLS ones included. Needs descriptor passing.
  • Record and replay: a bounded recording of everything nondeterministic a worker sees (completions, timers, wake-ups from other threads, received bytes), which the simulation driver replays exactly, so a failure in production becomes a test an agent can run. Needs the simulation driver.

Third wave, measured on bare metal:

  • Workers matched to the network card's receive queues, so a connection runs on the core its packets arrive on.
  • Elastic cores: a quiet service gathers its connections onto fewer workers and lets the rest sleep, and spreads out again under load, so several services share a small machine.

The cgroup's memory limit and its pressure signal (PSI) belong to the memory limit of 1.5, which reads them and tightens before the kernel's out-of-memory killer acts.

Done when: per item, as above. The track is done when every item has shipped in a 1.x release.

Speed work shipped in 0.5.0 too, each item with a benchmark showing what it buys:

  • Registered ring fd: about 11 ns saved of ~130 per io_uring_enter, which no benchmark of a whole server can see (neutral on bare metal); on by default from 5.18. Fixed files (direct descriptors) are not done: they would save about 11.5 ns per send, 0.6% of a request, less than keeping the descriptor table costs.
  • Zero-copy send for large responses: on bare metal, CPU time per request falls by 16% at 64 KiB, 62% at 256 KiB, 68 to 72% at 1 MiB and 85 to 86% at 16 MiB, at the same request rate (the link is full); bytes that cannot change only.
  • Receive buffers filled piece by piece (Linux 6.12): memory at 20 workers 49.9 → 23.4 MiB, requests per second unchanged.
  • Optional SQPOLL mode: tried and not merged. With its threads on CPUs of their own it lost on bare metal (8 workers and 8 kernel threads: 2.32M req/s against 2.41M for 8 workers alone, 73% more CPU per request, since the threads spin).
  • Kernel TLS (kTLS) for giong-tls: +36% serving 1 MiB files over HTTPS with sendfile on bare metal; slower than rustls from memory, so off by default (numbers).

0.3Prove itNovember 13, 2026The numbers so far come from a 4-vCPU virtual machine over loopback.

Executor, io_uring driver, TCP, UDP, files, timers, thread-per-core runtime, busy-poll mode, cross-thread channel, cancellation safety, backpressure, tests and benchmarks. See CHANGELOG.md.

Goal

The best async runtime for Rust, on technical merit: a complete, general-purpose runtime that fits any workload a service has, faster and leaner than Tokio, judged by measurements and not by adoption. Linux first: it makes the fewest possible system calls and keeps tail latency low by committing fully to io_uring and to one thread per core, and it still runs, on epoll, where io_uring is blocked.

giong is a late entrant, built for a time when AI agents write much of the code. Its API does not have to be short to type; it has to be strict, always correct, and able to grow for many years. After 1.0, giong stays on major version 1 and grows through 1.x minor releases (see Agent-first for the rules that make this possible). It replaces the Tokio ecosystem with crates of its own (HTTP server and client, TLS, DNS, database drivers) rather than adapting to it.

By 1.0, a team can write and deploy a real REST API (Postgres or MySQL, Redis, calls to other HTTPS services, HTTPS itself) with giong's crates alone, in an ordinary Docker or Kubernetes setup. Each crate that replaces a Tokio-based one is measured against it with a reproducible benchmark (tokio-postgres with deadpool, mysql_async and SQLx, redis-rs, reqwest, axum), and the README says where giong does not win.

After 1.0, the 1.x releases add gRPC, macOS, HTTP/3 and Windows, then a memory limit kept under any load, one at a time and without breaking the 1.0 API (see the milestones after 1.0 below). Alongside them, a third track fills in what a general runtime still lacks: blocking and compute work, processes and signals, structured concurrency, and scheduling that keeps a small machine efficient (see Runtime core). Linux stays the platform giong is tuned and measured on.

Agent-first

More and more code is written by AI agents, so giong is built for them to use correctly on the first try and to fix on their own when they get something wrong. That means removing vague conveniences and implicit defaults, never safety: the faster code is written, the tighter the checks around it have to be.

The 6 principles
  1. Errors explain themselves. Every error giong raises carries a stable code (GIONG-E0001…), says what went wrong and how to fix it, and links to a page about it. Functions keep returning io::Error; giong::error::code(&err) lets code, and agents, match on the code instead of the message.
  2. One obvious, correct way. No macros and no magic. Types strict enough that a mistake is a compile error: enums instead of flags and strings, Duration instead of a number of milliseconds, #[must_use] on futures and handles. No implicit defaults: every timeout and size limit is finite, documented, and visible in Debug output. Every addition to the API, through 1.0 and all of 1.x, follows four rules:
    1. One way to do each thing.
    2. Misuse fails at compile time, or at run time with a coded error.
    3. Every behaviour code relies on is documented.
    4. Releases only add; they never change what existing code means.
  3. Verification is the law. Tests, cancellation tests, ThreadSanitizer, loom, fuzzing and soak tests run in CI and block merging; cargo-semver-checks guards the API. Machines check the work, so human review is not the bottleneck.
  4. Documentation machines can read. AGENTS.md in the repository; llms.txt and llms-full.txt on giong.run, generated from the docs; a runnable example for every public API. Doctests are the source of truth.
  5. Observable from the inside. Per-worker statistics, connection-pool statistics and per-route latency, and structured logs as JSON lines. The runtime adds no dependency for this; tracing is an optional feature.
  6. An MCP server, giong-mcp. Attached to a running service, it lets an agent read the state of workers, tasks, connections, pools, statistics and profiles. Read-only, listening on localhost or a Unix socket, and only when the service turns it on.

Deliberate non-goals

These are deliberate. Proposals that need them will be declined.

  • The same tuning on every operating system. Linux is the platform giong is tuned and measured on, and io_uring stays the main path; the epoll driver (0.4) covers the Linux machines where io_uring is blocked, such as Docker's default seccomp profile. macOS (1.2) is for developing and testing on a Mac, and Windows (1.4) for services that have to run there. Both will pass the same test suite, but speed work lands on Linux first, and neither comes before 1.0.
  • Work stealing. A task that has started stays on its worker, so tasks need not be Send. Balancing happens where new work starts: Handle::spawn_balanced and TcpListener::bind_balanced.
  • Everything in one crate. giong is a runtime: it takes only what a runtime alone can do (scheduling, I/O, time, processes, memory, observation). Protocols, frameworks and tools are crates built on top of it, as giong-http, giong-web and the database drivers are. Network services come first and set the priorities, but blocking work, CPU-heavy work and child processes have a place in the runtime too (see Runtime core).
  • Send futures as a requirement. The API stays usable with Rc and RefCell.
  • Macros that hide control flow, and unbounded defaults. See Agent-first.
