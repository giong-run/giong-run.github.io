1.1.0latest

gRPC

November 21, 2026 · GitHub release · every commit

gRPC on giong: three new crates, giong-proto, giong-grpc-build and giong-grpc. Also HTTP trailers and streamed request bodies, a client that connects ahead of requests and pings idle HTTP/2 connections, batched PostgreSQL reads (off by default), faster large uploads, and a fix for an idle epoll worker spinning after a file operation. Nothing is removed or changed in meaning; upgrading from 1.0 needs no code changes.

Show the 21 changes in 1.1.0

Added

  • giong-http: trailer fields. Trailers holds the fields sent after a body. A streamed response ends with them through BodySender::send_trailers (a last HEADERS frame over HTTP/2, after the last chunk over HTTP/1.1), a handler reads a streamed request's with BodyStream::trailers, and the client reads a response's with StreamingResponse::trailers. Fields that mean nothing after a body (content-length, host, set-cookie and the like) are refused when trailers are built (GIONG-E1122, HttpInvalidTrailer) and dropped when they are received. Until now trailers were checked and dropped, which a request body received whole still does; a streamed one's trailers count against max_head_size over HTTP/2.
  • giong-http client: request bodies written piece by piece. RequestBuilder::streamed_body returns a RequestBody to send the pieces through, with backpressure, abort and send_trailers. Over HTTP/2 the response is read while the request is still being written, so requests and responses can alternate on one stream; over HTTP/1.1 the body is sent chunked and the response read after it. Redirects are not followed for such a request, and it is sent again after a refusal only if no piece had been taken.
  • giong-http: BodySender::closed waits until the client of a streamed response is gone (it reset the stream or its connection closed), for a handler that produces a response on its own and should stop when nobody reads it.
  • giong-grpc (new crate): gRPC servers and clients on giong-http's HTTP/2. The four kinds of call (unary, server streaming, client streaming, bidirectional), deadlines sent and enforced on both sides, cancellation that drops the server's handler, text and binary metadata, statuses with details, gzip per message, message size limits (4 MiB by default), TLS through ALPN. A streaming response's headers go out with its first message, or as a Trailers-Only response when the handler ends without sending one, as grpc-go and tonic do: metadata set before the first message still arrives first. giong_grpc::Server is a giong-http handler; a Channel shares HTTP/2 connections between calls. The statuses it raises itself carry GIONG-E4101 to GIONG-E4110 with the cause and the fix. Tested against grpc-go in both directions with the cases of gRPC's interoperability specification, on io_uring and epoll (giong-grpc/interop/run.sh, the gRPC workflow), and by hand against tonic 0.14.2's interop client and server (the eleven cases they implement). Measured against tonic 0.14 with bench/grpc.sh (4-core cloud VM, median of 10 rounds): a one-thread server does 30% to 50% more 100-byte unary calls a second, 21% to 25% more 10,000-byte ones, 48% to 50% more round trips on bidirectional streams and 3.8 to 4.0 times the messages of a server stream, and holds 5.7 kB instead of 11.6 kB per open stream. A one-thread client is level to 14% ahead (round trips against tonic's server, which that row measures: −1.7%). Tables and what was not measured: giong-grpc/README.md; raw data: bench/results/grpc/.
  • giong-grpc: health checking and server reflection. giong_grpc::health::Health serves grpc.health.v1.Health (Check, List, Watch) from statuses the program sets from any thread, with check and watch for clients; giong_grpc::reflection::Reflection serves grpc.reflection.v1 and v1alpha, so grpcurl lists, describes and calls a server's methods without its .proto files.
  • giong-proto (new crate): Protocol Buffers decoded as views over the receive buffer, with no copy and no allocation for strings, bytes, repeated fields and maps, and message structs whose fields borrow for encoding. Passes Google's protobuf conformance suite and is fuzzed against prost. Codes GIONG-E4001 to GIONG-E4008.
  • giong-grpc-build (new crate): generates the giong-proto messages and, for each service, a trait to implement, a server that routes calls to it and a client, from .proto files at build time. The files are parsed in Rust (protox): no protoc to install. The generated file also carries the descriptors reflection serves.
  • giong-http: Client::preconnect(url) opens a connection to an origin before the first request needs it (DNS, TCP, the proxy tunnel and the TLS handshake, with the client's settings) and returns the version it speaks, without sending a request. Requests made while it is being opened wait for it and share it once ALPN picks HTTP/2; when ALPN picks HTTP/1.1 the connection goes among the idle ones and the waiting requests open their own; when it fails or the call is dropped, the first request waiting opens one. No request is sent twice. Bounded by the client's timeout; cancel safe. Asked for in #154 by a service that warms its client up while requests arrive (#184).
  • giong-http: Client::ping_idle_http2(url, deadline) sends a PING on each idle HTTP/2 connection to an origin and waits up to deadline for the acknowledgements; it returns how many answered. A connection that answers counts as used (its idle timeout starts again). One that does not answer in time and still carries no request is closed at once and takes no more requests (GIONG-E1103); one that carried a request during the probe is left open. A probe in flight keeps the idle timeout from closing the connection, and a GOAWAY read with the acknowledgement fails the call (GIONG-E1106). Only acknowledgements of the client's own PINGs count. The client never pings unless asked. (#184)
  • giong-postgres: batched reads (Config::batch_reads, off by default). A pool sends the SELECTs waiting for one shared connection under one Sync, at most 16, never waiting for more, behind a prepared statement that makes their transaction read-only. The server replies and wakes the client once per batch instead of once per statement: with the database as the limit, 3.4 times the one-row lookups (198.3k against 58.7k a second on one server core, p99 0.56 ms against 2.0 ms), 18% more on three cores, nothing for 100-row reads, and little on the full path of an HTTP request (bench/db-path.sh, new), where the HTTP side is the limit. A SELECT that writes fails in the batch with 25006 and is sent again alone; statements the server skipped after an error in their batch are sent again one by one, as are the other statements of a batch that a failure or a failed commit rolled back. A SELECT that calls set_config runs alone, so that a transaction-local setting does not reach other tasks' statements; not for functions that make such settings (row-level security set up per request), which a statement's text does not show. A batch holds the locks its statements took until it ends, so a statement of a batch gives up a lock wait within 50 ms, and one that fails in a batch with a lock timeout, a deadlock or a serialization failure is sent again alone: a batch cannot deadlock with a transaction that its statements one by one would not (a migration locking two tables). MySQL's protocol has no equivalent.
  • bench/db-path.sh: an HTTP request that reads one row from PostgreSQL or MySQL, answered as JSON, on giong against axum with deadpool-postgres and with SQLx, for throughput, p50/p99 under load and the latency of one request at a time.

Changed

  • giong-http client: HTTP/2 requests sent with send_streaming carry te: trailers, since their trailers can now be read; servers that only send them to a client that asks (gRPC) do so. Requests sent with send are as before.
  • giong-http client (performance): a request costs 1.0% to 1.4% more instructions than in 1.0.0-rc.1 (bench/instr: http1-client 30,512 to 30,939, h2 43,059 to 43,563, https 42,596 to 43,175 on io_uring), the price of request bodies that can be streamed; allocations and the memory of idle connections are unchanged. The baseline is updated.
  • giong-http (performance): the HTTP/2 server puts the small pieces a handler sends one after the other through BodySender::send into one DATA frame (up to 16 KiB) when they are ready in the same turn of the connection, and lets handlers that were woken while it polled them go on for up to 32 rounds before it writes, instead of a frame and a write for each piece. send waits for the connection to take each piece as before.
  • giong-http (performance): the HTTP/2 server sends the answers to a burst of short requests in one write: answers whose bytes fit in one DATA frame fill the output up to 768 KiB, where it stopped at 64 KiB, and with one write in flight a connection waited a turn of the worker for each further write. Streamed and file bodies still stop at 64 KiB. The bytes in the output now count against the connection's budget for unsent responses until they are written, so a connection holds no more than before. 10,000-byte gRPC unary calls from tonic's client on one server thread (bench/grpc.sh, 4-core cloud VM, io_uring): 62,597 to 89,862 calls a second with 16 in flight per connection.
  • giong-http client (performance): over HTTP/2, StreamingResponse::chunk hands over a received DATA frame's buffer as it is (small frames still arrive joined) instead of copying the frames that wait into one piece. Pieces stay within 64 KiB as documented.
  • giong-http: a request body of 64 KiB or more is received straight into the request buffer, instead of being copied there out of the runtime's receive buffers. Uploads of 1 MiB are 2.2 to 2.3 times as fast and use 53 to 58% less CPU, on both drivers (3 MiB: 2.4 to 5.2 times), and small requests on the same connections are 1.2 to 1.4 times as fast; memory per idle connection and small requests alone are unchanged (#194, bench/results/upload-recv-into/).
  • giong-http (memory): an idle server connection holds 8 bytes more over HTTP/1.1 (bench/instr idle heap: 1,979.9 to 1,988.2 bytes on io_uring, 2,158.1 to 2,166.1 on epoll) and 24 bytes more over HTTP/2 (4,473.4 to 4,497.4 and 4,555.6 to 4,579.6), against the 1.0 baseline; within the 1% that bench/instr allows. Which 1.1 change adds it is not isolated yet.

Fixed

  • giong: an idle worker on the epoll driver no longer spins at full CPU after a file operation. A blocking job that finished while its worker took the results rang the worker's bell after the results were gone; the bell stayed readable with nothing to take, and every later wait ended at once until the next file operation finished. The wait that sees such a ring now resets it.
  • giong-http: on an HTTP/2 connection with more streamed request bodies open at once than the body budget has full windows for (from the fourth, with the default budget of 1 MiB), the streams after the first few were never given flow-control window again once they had used the window they started with, although their handlers had read everything: they stalled until an older stream ended, and for good next to streams that never end (bidirectional gRPC streams, long uploads read as they arrive). A stream whose handler has taken what it sent now gets back the window it started with, which the budget keeps for it while it is open; windows beyond that are still granted only within the budget. A body received whole before its handler runs holds what it received, so it gets no window past the budget. Found with 16 bidirectional gRPC streams on one connection, of which three made progress.
  • giong-http: a timeout of Duration::MAX (or anything past what the clock can add) given to Server::idle_timeout, request_timeout, write_timeout, shutdown_linger, ClientBuilder::timeout, connect_timeout, idle_timeout or RequestBuilder::timeout panicked when it was added to the clock, in the connection's task. Such a timeout now counts as a century: no timeout.

Show the change in 1.0.1

Fixed

  • A worker with spin_before_park could stop blocking for good and burn its core: the io_uring driver counted the kernel's deferred-work flag (IORING_SQ_TASKRUN) as completions waiting, and Linux 6.18 (DEFER_TASKRUN) can leave that flag set after the work has run. The spin loop then found "work" on every look, entered the kernel, found nothing and looked again, at 100% CPU and without ever reaching its other checks. Seen in about one of 70 runs of a benchmark streaming 10 million messages between two processes. The driver now runs the deferred work and lets the completion queue decide.

1.0.0-rc.1

Stable

November 20, 2026 · GitHub release · every commit

Show the 43 changes in 1.0.0-rc.1

Security

  • giong-http: the server refuses new connections while the process is close to running out of memory, instead of taking on connections until the kernel's out-of-memory killer ends it with every connection it holds. Before each accept it checks what is left (the smaller of what the process's cgroup allows, page cache aside, and the machine's MemAvailable), and below a reserve it answers new connections without TLS with 503, Retry-After: 1 and GIONG-E1121, and closes new TLS connections before their handshake; the connections it holds keep being served. The reserve is Server::min_free_memory (new), by default a tenth of the memory limit, between 16 and 256 MiB; 0 turns the check off. Found on bare metal in a container of 1 CPU and 512 MiB, where 0.8.0 was killed at 36,400 idle HTTPS connections (with max_connections raised); the default limit of 10,000 connections per worker was enough to get it killed in smaller containers too: 7,900 idle HTTPS connections in 96 MiB, or 9,100 plain ones in 32 MiB (cgroup v1, which leaves kernel socket memory out). With the check, the same runs refuse at 6,500 and 6,600 connections and stay up. CI runs it in a container of 48 MiB with one and four workers on both drivers (scripts/idle-connections.sh).

Added

  • All crates: every public async fn says in its documentation whether it is cancel safe and, when it is not, what a dropped future leaves behind (a statement that may still run, a datagram that may be sent, a file that may be created). tests/cancel_docs.rs fails a public async fn without it.
  • Docs: docs/STABILITY.md says what a cancelled operation does on both drivers (it may still happen; buffers and descriptors stay with the driver until the kernel is done with them; a close is never cancelled; a transaction never commits a statement whose outcome it does not know) and which limits wait and which refuse by default, which 1.x will not change. docs/RELEASING.md gives the checklist a 1.0 release candidate carries: the soaked commit, the release commit, what changed between them, the tests run again and the soak that change got, sized by what changed (none, 2 to 4 hours, or 72).
  • giong-tls: TlsConnector::with_root_pem_any_name(pem) trusts the given authorities without checking the host name (ssl-mode=VERIFY_CA in giong-mysql, which now uses it instead of a rustls verifier of its own). CertificateDer (from rustls-pki-types 1.x, what TlsStream::peer_certificates returns) is re-exported.
  • giong-tls: the server side without rustls' types. Certificates holds one or several certificate chains: TlsAcceptor::with_certificates presents the one valid for the name the client asks for (SNI), and Certificates::replace_pem swaps the set while the server runs, for renewed certificates. TlsAcceptor::require_client_cert and request_client_cert turn on mutual TLS. The post-quantum feature uses aws-lc-rs and offers the X25519MLKEM768 key exchange first. New error code GIONG-E2013 (Code::TlsConfig) in giong.
  • giong-http: Server::min_free_memory, and the error code GIONG-E1121 (Code::HttpServerLowMemory) in giong.
  • giong-mysql, giong-redis (behaviour change): Pool::idle_timeout, Pool::max_lifetime and PoolStats::recycled, with giong-postgres's defaults and meaning, so the three pools are configured the same way before the 1.0 API freeze. A pooled connection unused for 10 minutes is now closed, and one older than 30 minutes (less up to a tenth at random) takes no new statement or command and is closed once the ones on it are answered, or when it comes back from get() or take(); the pool opens another when needed. Before, a connection stayed open until the server or the network closed it, so a pool kept talking to the old primary after a DNS failover. giong-redis reads no clock on the path of a shared command for this: a command marks its connection used, and the pool's sweep, which runs every quarter of the shorter of the two settings (at most every 30 seconds), turns the mark into a time. observe snapshots and giong-mcp report recycled for the two pools.
  • giong-postgres, giong-mysql: Error::server_code(), the name giong-redis already used for the code the server sent (code() named a different thing in each crate), and Error::is_transient(), as giong-redis and giong-http's client have: true for a failed connect, a closed connection, a pool timeout, and the server errors a retry can cure (giong-postgres: class 08, 40001, 40P01, 55P03, 53300, 57P01-57P03, 25006; giong-mysql: 1213, 1205, 1040, 1203, 1053, 1792, 1836, 1927, and 1290 for a read-only server).
  • giong: sync::mpsc::unbounded(), the new name of sync::mpsc::channel(). Tokio's mpsc::channel(n) is bounded, so code ported from Tokio, or written from memory of it, took giong's channel() for a bounded channel; bounded(n) is that one here. Its halves are now UnboundedSender and UnboundedReceiver, as in Tokio, and the short names Sender and Receiver go to the bounded channel, whose memory has a limit (see Removed).
  • giong-postgres: Config::database, the name giong-mysql and giong-redis use. The URL parameter is still dbname, as libpq spells it.

Changed

  • Breaking: giong-mcp: FromEnv is #[non_exhaustive], like every other enum that is not complete by nature, so a match on it needs a _ arm. FromEnv::server() and FromEnv::error() are unchanged.
  • giong-tls (breaking): rustls' types are out of the stable API, so that a new rustls version, which giong-tls will take up during 1.x, breaks nothing. The rustls configurations that TlsAcceptor::new and TlsConnector::new took go to the new TlsAcceptor::from_rustls and TlsConnector::from_rustls, which need the new unstable-rustls feature, as do KtlsSupport::supports and the rustls re-export (no longer there without it). That feature is outside the semver promise: it follows the rustls version giong-tls uses.
  • giong-tls (behaviour change): TlsAcceptor::from_pem picks AES-128-GCM first of the cipher suites both sides allow, whatever order the client lists, as Go's and BoringSSL's servers do; a client that lists ChaCha20-Poly1305 before every AES-GCM suite (one without AES instructions) still gets ChaCha20. OpenSSL's clients (wrk, curl, Python) list AES-256-GCM first, whose TLS 1.3 suite hashes with SHA-384, about a sixth of a resumed handshake's CPU time. With bench/tls.sh (4-vCPU VM, 7 rounds, raw data in bench/results/tls/), new connections went from 6.8k to 8.4k per second (142 to 116 µs of CPU each) together with the next entry, against 7.1k for axum + rustls; axum set to the same order reaches the same 8.4k, so the suite is most of the gain. 64 KiB responses went from 26.3k to 31.9k per second. An acceptor made with TlsAcceptor::new uses its configuration as given.
  • giong-tls: fewer TCP segments per connection. A TLS 1.3 server's session tickets wait for its first response, or for a receive that has to wait, instead of going out alone; later key updates answering the peer's wait the same way; shutdown sends close_notify with MSG_MORE, so it shares the FIN's segment; and the pieces of one vectored write share one send. Per Connection: close request, both directions: 14.4 segments against 16.5 (axum + rustls: 14.0), and p99 latency 4.2 ms against 5.8.
  • giong-compat: a write at least as large as the write buffer's limit (64 KiB by default), with nothing buffered or being sent before it, goes straight from the caller's memory to the socket in one sendmsg(2) that does not wait, as BufWriter and Tokio's streams do, instead of being copied into the buffer first; what the socket cannot take at once is still buffered. bench/compat.sh (raw data in bench/results/compat/): CPU per KiB sent 378 ns against 400 for 0.8.0's Compat, and within 2–9% of Tokio over two sessions (0.8.0's measured 25% above it the same morning). Receiving is unchanged by it: 30% more CPU per byte than Tokio with read, 17% with AsyncBufRead, most of it in giong's own receive; 19% and 14% with the 16 KiB receive buffers below, where Compat sends at 6% less CPU per KiB than Tokio.
  • giong-tls (behaviour change): TlsStream::shutdown returns Ok when the close_notify cannot be sent because the peer has closed its socket already (EPIPE, ECONNRESET): the sending direction is closed either way and nobody is left to tell. An h2 server over Compat reported such a client's clean departure as an error.
  • giong-postgres, giong-mysql, giong-redis: on plain TCP and Unix sockets a connection has the kernel write what the server sends straight into its read buffer (a one-off receive of up to 64 KiB) instead of copying it there from the runtime's pooled buffers, so each byte is copied once on the way in instead of twice. Measured with bench/redis.sh, bench/postgres.sh and bench/mysql.sh (medians of 5 rounds, bench/results/): giong-redis GET of 8 KiB values with four connections went from level with redis-rs (259k against 269k per second) to 345k against 276k, and with one connection from about 240k to 375k (redis-rs 151k); giong-postgres's pool of 4 from 243.9k to 303.8k point lookups and 53.9k to 72.9k 100-row reads; giong-mysql's from 138.1k to 152.1k and 34.3k to 38.3k; with pools of 3 (the size the READMEs advise for a 3-core server), 240.7k to 311.4k and 138.7k to 150.7k point lookups. Small Redis commands are unchanged. Each connection's read buffer now keeps 64 KiB of room (it was 8 or 16 KiB, with the received bytes in the runtime's shared pool). TLS connections read as before. giong-postgres with one connection shared by every task stays 7–9% behind tokio-postgres (47.7k against 51.4k point lookups): the server is the limit there and spends half its time sending one reply per statement; the giong-postgres README says why it does not merge statements under one Sync.
  • giong-http: the client's RequestBuilder::header takes impl AsRef<str> for the value, as the server's Response::header does, so .header("X-Id", id.to_string()) needs no &. A call that passed a &str or &String compiles as before; one that relied on the parameter being &str to infer a type (value.as_ref(), .into()) now needs &str written out. cargo-semver-checks reports no break.
  • Docs: giong-web's Router::layer and README say that the first middleware added is the outermost, the reverse of axum's Router::layer, so code ported from axum lists its layers the other way round.
  • Docs: CONTRIBUTING.md lists every fuzz target (response_body, the PostgreSQL and MySQL session targets and the resolver's two were missing); giong-http's Response::json says it sends bytes that are already JSON; the API freeze record (docs/reviews/2026-11-api-freeze.md) gains the items of the reviews it had left out.
  • net: UDP is faster than Tokio's on io_uring and level with it on epoll, on a cloud VM. A UDP echo server on one core (64-byte datagrams, veth, bench/udp-echo.sh, 5 rounds, bench/results/udp-echo/) answers 328,000 datagrams a second with 16 tasks on one socket on io_uring (259,000 before, Tokio 278,000) and 300,000 with one task (286,000 before, Tokio 259,000); on epoll 284,000 in both cases (239,000 and 258,000 before). UdpSocket::send_to and send send within the call when the socket has room, instead of through an operation that waited a turn of the event loop (io_uring) or allocated a message header (both), and use sendto(2) rather than sendmsg(2). The epoll driver receives up to 16 datagrams with one recvmmsg(2). An echo now costs one system call on either driver where Tokio makes two. Immediate sends count against the task's budget, so a task that only sends still gives way to the others. On bare metal (AMD EPYC 4345P, Linux 7.0, the same benchmark; bench/results/bare-metal-epyc-4345p/linux-7.0/post-soak/udp-udp-faster-*) the server core is saturated near a million echoes a second and the runtimes are close: this change is behind Tokio with io_uring and 16 tasks (856,000 against 870,000) and with epoll and one task (874,000 against 882,000), level with epoll and 16 tasks (879,000), and ahead with io_uring and one task (926,000 against 882,000).
  • net: the epoll driver's UDP path is close to the kernel's ceiling. The same echo server answers 336,000 datagrams a second with 16 tasks on epoll (284,000 before, Tokio 271,000, the kernel-only recvmmsg/sendmmsg server 390,000) at 4.08 µs of server CPU per echo (5.07 before, Tokio 5.33, kernel 3.55), and 351,000 with one task (284,000 before, Tokio 307,000) (bench/results/udp-echo/vm/epoll-deep/), on a cloud VM. Two changes: datagrams that tasks send while other tasks of the worker are runnable go to the kernel at the end of that turn of the event loop, in one sendmmsg(2) per socket, each sender still getting its own result and datagrams of one socket keeping their order (both drivers; a lone sender sends at once); and on epoll a datagram socket that has received 64 datagrams leaves the epoll set until a task has to wait for it again, because in the set every datagram received and every one sent and freed wakes epoll's callback on the socket's wait queue. On bare metal (post-soak/udp-udp-epoll-*, as above) the margins are small: with 16 tasks 921,000 on epoll and 902,000 on io_uring against Tokio's 870,000, ahead in every round; with one task 893,000 and 876,000 against 863,000, a tie within the noise between rounds.
  • runtime, sync, time, fs, net: the core of the runtime is faster than Tokio's in every workload of the new bench/core.sh, which runs the same code on giong, Tokio (current-thread, LocalSet and multi-thread), monoio, glommio, compio and smol. Medians of 5 rounds on the 4 vCPU cloud VM, ns per operation, io_uring (bench/results/core/vm/): spawning and joining a task 92 (184 before; Tokio 174 to 226), a thread outside the runtime feeding a task over mpsc 64 (194; Tokio 155 to 167), one task feeding another 31 (40; Tokio 58 to 62), a chain of 1,000 tasks passing a token 220 (270; Tokio 289), a task sleeping once among 100,000 688 (748; Tokio 886 to 935), a loopback TCP round trip with both ends on one thread 4,650 (4,930; Tokio 5,230). On epoll, two tasks bouncing a value over channels take 222 instead of 531 (Tokio 481); the TCP round trip there is level with Tokio's (5,304 against 5,231, the same system calls). monoio and glommio stay ahead on spawning and on their channels, which only work within one thread; giong's channels also carry values between threads. The changes:
    • a task and its join state are one allocation, the waker a poll lends the task holds no reference count of its own, and a finished task's waker state serves the next spawn when no waker of it is left;
    • the unbounded mpsc receiver takes everything queued under one lock when its own values run out, instead of locking once per value;
    • sleeps polled in the same turn of the event loop share one clock reading; a deadline within a millisecond of it reads the clock again, so a zero timeout still ends at once;
    • File::read_at (and so fs::read) first tries preadv2 with RWF_NOWAIT, which copies from the page cache without waiting for the disk, and goes to the driver only when that returns nothing; fs::read takes its size hint from fstat;
    • on io_uring, a TCP or Unix stream send by the only runnable task goes out with send(MSG_DONTWAIT) instead of waiting a turn of the loop for its completion (with other tasks runnable, sends still reach the kernel together through the ring, and no send can overtake one still in the ring);
    • on epoll, a busy worker looks for I/O every 61 polls, as Tokio does, instead of making an epoll_wait call at every turn of the loop.
  • runtime: the default receive buffers are 16 KiB instead of 8 KiB (Builder::recv_buffers(512, 16 * 1024)). Each receive brings at most one buffer, so a bulk receive takes half the receives: giong's own recv of a 2 GiB stream spends 124 ns of CPU per KiB instead of 142 (Tokio 120; medians of 7 interleaved rounds, bench/compat). The memory a worker reserves for its pool doubles, to 8 MiB of address space, of which it touches only the buffers it lends (16 at first): measured with bench/memory.sh (10,000 connections, 4 workers), memory per open, idle and pending connection and the peak under load did not change. On kernels without packed buffers (before 6.12), where every stream receive takes a whole buffer, a buffer the application holds now pins 16 KiB instead of
    1. A datagram received with recv_from can now carry up to 16 KiB − 44 bytes before it is cut off.

Fixed

  • giong-postgres: a Transaction in which a statement was given up before its answer came (its future dropped, by a timeout say) could still commit, although the statement may have run on the server unseen. As in giong-mysql, the transaction now refuses every later statement and commit with an ErrorKind::Db error that says so, sends nothing more, and is rolled back when dropped. In both crates a statement whose answer had arrived before its future was dropped no longer counts, since its outcome is known (giong-mysql refused the commit for it too).
  • A File::close whose future was dropped after it was first polled could leave the descriptor open with nobody owning it: on the epoll driver when no blocking thread had started the close yet, and on io_uring when the kernel had handed it to a worker thread (network filesystems, FUSE). The close is no longer cancelled; it runs to the end and only its result is lost.
  • net: tasks that share a UdpSocket and wait in recv_from at the same time are each woken for a datagram of their own. On io_uring they shared one wake-up slot: only the last task to wait was woken, the others saw their datagrams only when something else woke them, and a server of 16 tasks on one socket made one kernel entry per datagram. A task that stops waiting (its receive timed out) no longer takes the wake-up of the next datagram.
  • giong-http: requests sent at once to an https origin the client had no connection to yet each opened a connection and did a TLS handshake of their own, up to max_connections_per_host, because the pool learned that the origin speaks HTTP/2 only once the first handshake was over. They now wait for that first connection while ALPN may still pick HTTP/2, and share it when it does; when it picks HTTP/1.1 they open their own as before, and when the first one fails or is dropped the next in line opens one. 64 requests to a new loopback origin on one worker: 16 TLS connections and 4.70 ms before, 1 and 0.78 ms after (median of 21 rounds). Reported from a service that warms its client up while requests arrive (#154).
  • UdpSocket::bind to a port no other socket of the process held could fail with AddrInUse for a port that nothing held, while any thread of the process read /proc/self/fd (lsof, ss -p, monitoring agents, giong-mcp's count of open descriptors). The first bind of a port checked it with a probe socket, bound and closed again; a socket closed while such a reader holds it keeps its port for a few microseconds, and the real bind came right after. The first socket of a port is now bound without SO_REUSEPORT itself and sets it once bound, so nothing is closed before the bind. TcpListener::bind takes the same path (it was not affected). Seen as the rare AddrInUse of the UDP rebind test on CI; reproduced without giong at 8 to 105 refused binds in about 119,000 with two threads reading /proc/self/fd, none without.
  • giong-postgres: Pool::max_lifetime(Duration::MAX) panicked with an overflow when the pool opened its first connection (the random part of the lifetime was computed as a tenth of it times up to 999); a lifetime too long for the clock now means none, as wait_timeout(Duration::MAX) does in giong-redis. Found while adding the same setting to the other two pools.
  • giong-tls: a cancelled TlsStream::recv could end the stream's sending for good. A receive with nothing to read first sends what the connection owes the peer (a TLS 1.3 server's session tickets after the handshake, the answer to a key update); on io_uring that send stayed with the kernel across the poll, and a receive dropped then (a short timeout, a select) left the record stream cut, so every later write failed with GIONG-E2008. Such records now leave in one send(2) that does not wait: what the socket takes is sent, the rest goes out first with the next send or receive, in order, and no receive holds a send that dropping it could cut. With kernel TLS the answer to a key update and alerts go the same way, and a key update the socket has no room for is paid by the next send. recv is cancel safe without exception; its documentation said otherwise. Found as a rare failure of recv_is_cancel_safe under ThreadSanitizer.
  • giong-tls: with kernel TLS, a KeyUpdate asking for new keys that reached the socket together with the end of the handshake (a peer that renews its keys at once) was never answered, and the peer could not decrypt anything sent to it afterwards. The handshake read whatever had arrived, rustls took the KeyUpdate, changed its sending key and kept the answer for a write that never came once the keys went to the kernel. The handshake now reads record by record from the moment this side has sent its first flight, so every record after the peer's last handshake record stays in the socket for the kernel, which answers the key update like any other. A kernel TLS handshake makes a few more small reads for it (two per record of the peer's later flights); handshakes in the process are unchanged.
  • giong-tls: the fix for a cancelled recv above made every idle TLS connection hold the buffer its session tickets had passed through: about 200 bytes more heap per idle HTTPS connection (10,981 bytes on io_uring against the 10,784 recorded before it). The buffer is now given back as soon as it is empty: 10,798 bytes on io_uring and 10,849 on epoll (instr, 2,000 idle connections), within 30 bytes of the figures recorded before the fix (10,784 and 10,821). What stays of that fix's cost is one field in the stream and two checks per write: 0.4% more instructions per HTTPS request (44,780 against 44,604 on io_uring, 43,255 against 43,090 on epoll).
  • giong-http: an idle HTTP/2 connection took 61% more resident memory in 0.8.0 than in 0.5.0 (6.78 KiB against 4.21 on bare metal, bench/h2.sh, 5,000 connections that made one request each). Since 0.8.0 a connection kept the memory for its streams for a second after each request, so that requests following one another allocate none of it: when thousands of connections open together, all of them held it at once, and the allocator kept the pages after it was freed. A connection now keeps it only once a request has followed another within that second. Since 0.6.0 the queue of handlers to start also reserved room for four requests (672 bytes) on its first use; it now starts with room for one, as the slots for streams now do too (they took room for four, 1,408 bytes). Measured on a 4-vCPU VM (Linux 6.18, bench/hold, 5,000 connections, one worker), resident memory per connection, 0.5.0 / 0.8.0 / now (raw data in bench/results/low-memory/): idle 4.56 / 7.09 / 4.54 KiB, one request in progress 6.68 / 7.42 / 5.88 KiB, ten requests in progress 19.09 / 21.65 / 19.09 KiB. The instr job did not catch it: its idle-h2 case opened connections without making a request. It now makes one on each, as bench/h2.sh does.
  • giong-http: the first version of the fix above, merged in #125, gave the queue of handlers to start back each time it emptied after growing past four. A client with many streams in flight grows and empties it all the time, so every burst allocated it again: on bare metal HTTP/2 served 4.6% fewer requests per second (1.519M against 1.593M, bench/h2.sh json). The queue is now given back after the first burst only, which keeps ten long requests opened at once from holding it, and kept from the second on until the connection is idle. Instructions per request against 0.8.0 (callgrind, h2load with 10 connections, 4-vCPU VM; raw data in bench/results/low-memory/): one stream at a time +1.2% before, +0.4% now; ten streams +2.1% / +0.3%; a hundred +4.5% / +1.1%. Memory stays as above. The instr job sent one request at a time and missed it; its new h2-streams case sends ten at once on one connection, with a limit of 0.5%.
  • giong: UnixStream::recv could miss the end of the stream on Linux 6.18 with io_uring, and wait until the peer closed the socket. When the last data arrived together with the peer's shutdown(Write), the kernel's multishot receive took the data and went back to waiting without reporting the end (a bare ring without giong does the same on 6.18.44 and 6.18.63, with more than 32 buffers of data waiting; 6.12.117 and TCP sockets do not). A reader that has taken everything received from a Unix socket now asks the socket whether the peer has stopped sending, with one poll call, and starts the receive again if it has. An echo over a Unix socket whose client writes, shuts down and reads to the end stalled about once in 8,000 runs with four of them in parallel; with the check, 480,000 runs had none. The epoll driver was not affected. Sockets from UnixListener::accept also no longer try a zero-copy send first, like the other Unix sockets.

Security

  • giong-http (hardening, behaviour change): the requests a worker is receiving in full now share a memory budget, Server::max_buffered_request_bytes. Before, each connection was bounded (max_head_size, max_body_size) and so was the number of connections, but not the sum: with the defaults about 11 GiB per worker, and 130 clients each sending a 1 MB body one byte short got a one-worker server in a 128 MiB container OOM-killed (axum with a Bytes route dies at the same point). The budget is 64 MiB per worker by default, or a quarter of the process's cgroup memory limit divided among the workers if that is less (32 MiB for one worker in 128 MiB), and never less than one request at max_head_size plus max_body_size. Bytes count as they arrive, not as announced, from HTTP/1.1 heads and bodies (the first 4 KiB of each request excepted, so ordinary requests keep being served) and HTTP/2 bodies, until the request is dropped. A request that does not fit is refused without calling its handler: over HTTP/1.1 with 503 Service Unavailable, Retry-After: 1 and Connection: close, before its body is read when its Content-Length already does not fit; over HTTP/2 with REFUSED_STREAM, which clients retry and which does not count against the client's reset budget. A request larger than the whole budget gets 413. New code GIONG-E1120 (Code::HttpServerBusy), named in the 503's body and in a line on stderr at most once a minute per worker. What changes for a running service: under many large uploads at once, requests past the budget get 503 instead of being buffered; streamed bodies (Handler::stream_body) are not counted. With the fix, 450 such uploads (300 over HTTP/1.1, 150 over HTTP/2) leave a one-worker server in a 128 MiB container at a 35 MiB peak. CI runs the attack in a 128 MiB container on every change (slow-uploads job, scripts/slow-uploads.sh). The max_connections documentation no longer says that the connection limit alone keeps memory bounded; docs/DEPLOYMENT.md has a section on sizing a container.

The first round of reviews before 1.0, fixed. Three of the bugs fixed here are in 0.5.0 and worth knowing about for anyone who runs it. There is no 0.5.1; the fixes are in this release only.

HTTP/2, and less work per byte. giong-http speaks HTTP/2 as a server and as a client, through ALPN or with prior knowledge, with the same handlers; it is hardened against rapid reset, floods and HPACK bombs, h2spec passes all 147 cases, and on one core of a bare-metal server it answers 2.3 to 4.3 times as many HTTP/2 requests as axum. giong-tls can hand a connection to the kernel's TLS after the handshake, and files go out with sendfile: on bare metal a 1 MiB file over HTTPS is served 36% faster than with rustls, level with nginx. On io_uring, large static bodies leave without a copy on Linux 6.2 and newer (up to 85% less CPU per request), connections share receive buffers piece by piece on 6.12 and newer (less than half the memory under load), and bulk receives are no longer copied out of the pool. SQPOLL was tried and left out: on bare metal it served fewer requests with 73% more CPU per request. The new giong-compat gives giong's streams the Tokio and futures-io I/O traits, so crates such as h2, tokio-rustls and tokio-tungstenite run on giong. On Linux 6.14 to 7.2, a worker past the locked-memory limit now runs on epoll and says why (GIONG-E0010) instead of stopping the runtime. No change breaks code written for 0.4, but a stream's recv may now return one write of the peer in two pieces.

The release candidate was measured again on the two bare-metal machines (bench/results/bare-metal-epyc-4345p/linux-7.0/release-0.5.0/): on 4 workers giong served 1.75M requests/s against 1.69M for tuned Monoio and 1.59M for raw Tokio, two 15-minute soaks passed, and nothing moved beyond the 2% noise between runs except two small losses not explained yet: an idle HTTP/2 connection costs 4.21 KiB where an earlier build measured 3.99, and giong-http over TLS answers about 2% fewer small requests.

Added

  • giong-http: HTTP/2 (RFC 9113) for the same handlers. Over TLS, serve_tls offers h2 and http/1.1 through ALPN, so browsers get HTTP/2; without TLS, a connection that opens with the HTTP/2 preface is served over HTTP/2 ("prior knowledge"), on the same port as HTTP/1.1. Each stream is a Request like any other, so handlers and giong-web apps serve HTTP/2 unchanged; Request::version() returns the new Version (Http10, Http11, Http2). Flow control both ways, HPACK with its dynamic table, streamed bodies both ways, file bodies (Body::File, read in 64 KiB pieces into DATA frames; a file shorter than announced resets its stream), Expect: 100-continue, trailers, and graceful shutdown with a GOAWAY after which the streams in progress finish. A stream the client resets drops its handler at once. Server::http2(false) serves HTTP/1.1 only, and Server::max_concurrent_streams (default 100) caps the streams of one connection. h2spec passes all 147 cases over TLS in strict mode, and runs in CI.
  • giong-http: every resource an HTTP/2 client can make the server hold is bounded, and a client that overdraws a limit gets a GOAWAY whose debug data carries a code with a page in docs/errors: GIONG-E1115 (protocol error), GIONG-E1116 (rapid reset: too many streams reset or refused), GIONG-E1117 (a flood of frames that do no work: PING, SETTINGS, PRIORITY, empty DATA or CONTINUATION, needless WINDOW_UPDATE) and GIONG-E1118 (a header block larger than max_head_size, the CONTINUATION flood). A header list that decodes larger than max_head_size (an HPACK bomb) is answered with 431. Request bodies are received only as fast as the handler takes them, and the bodies one connection holds share a budget (the larger of max_body_size and 1 MiB) instead of growing with the number of streams; a client that stops reading stops being read from, and a stream its flow control keeps waiting longer than write_timeout is reset.
  • giong-http: on one core, HTTP/2 serves 3.8 to 4.4 times the requests per second of axum 0.8 (hyper) on small answers and 2.5 to 3.0 times on 8.5 KiB ones, over HTTPS and with prior knowledge (502k against 131k for a 27-byte answer over HTTPS). An idle HTTP/2 connection costs 4.2 KiB (axum 23.8), one with a request in progress 5.9 KiB (23.0), and each further request 1.1 KiB (2.0); an idle HTTP/1.1 connection still costs 1.9 KiB. bench/h2.sh measures both; results are in bench/results/h2/.
  • giong-http: HTTP/2 in the client. https connections offer h2 and http/1.1 through ALPN, and a server that picks h2 gets every request to its origin on one connection, as many at once as it allows (another connection is opened, up to max_connections_per_host, when it allows no more). ClientBuilder::http2(false) sticks to HTTP/1.1; ClientBuilder::http2_prior_knowledge(true) speaks HTTP/2 to http URLs (gRPC backends, giong-http's own server). Response::version() and StreamingResponse::version() say which was spoken. What a server can make the client hold is bounded by the windows it grants (1 MiB of each response body, 4 MiB on a connection, granted again only as bodies are read). A request the server refused unprocessed (REFUSED_STREAM, or beyond the last stream of a GOAWAY) is sent again whatever its method; a dropped request or streamed response resets its stream, and the connection carries on. Redirects, decompression, streamed bodies, timeouts and the limits work as over HTTP/1.1.
  • giong-http: over HTTP/2, the client on one core sends 2.0 to 2.2 times the requests per second of reqwest 0.12 on small answers (251k against 123k over HTTPS) and 1.2 to 1.3 times on 8.5 KiB ones. bench/http-client.sh measures HTTP/2 over TLS and with prior knowledge (h2, h2c), and tells both clients to speak HTTP/1.1 for http and https.
  • Kernel TLS in giong-tls: TlsAcceptor::ktls(mode) and TlsConnector::ktls(mode) hand a connection's keys to the kernel once rustls has done the handshake, and the kernel encrypts and decrypts from then on; the TlsStream API stays the same. Ktls::Off is the default; Ktls::Auto uses the kernel where it can do everything rustls would have done (the tls module, every cipher suite the configuration allows in both directions, and new TLS 1.3 keys on a live connection, Linux 6.14+) and keeps the connection in the process otherwise; Ktls::Required fails with GIONG-E2009 instead. What the kernel can do is probed once per process (giong_tls::ktls_support(), one line for a log); TlsStream::is_ktls(), ktls_unavailable() and giong_tls::ktls_stats() say which way connections went. Session tickets, key updates from either side, alerts, refused renegotiation and close_notify work as with rustls in the process. The TLS 1.2 AES-GCM handoff starts the kernel's explicit nonces past every nonce rustls used: handed rustls' IV as it is, the kernel would repeat the nonce of the Finished message under the same key. New error codes GIONG-E2009 to GIONG-E2012 explain each failure. Linux 6.0's kernel TLS is refused (it can crash the kernel when a connection closes); 5.15 and 6.1 on are tested.
  • Files over TLS without copying them: giong::net::TcpStream::send_file(&file, offset, len) sends a range of a file with sendfile(2), straight from the page cache, on both drivers; with kernel TLS the kernel encrypts the file as it sends it. giong_tls::TlsStream::send_file does that under kernel TLS and reads and encrypts in 256 KiB pieces in the process otherwise. giong-http sends the new Body::file(file) and Body::file_range(file, offset, len) that way (Transport::write_all_with_file; Unix sockets read and write). A file that turns out shorter than announced is the new error GIONG-E0201 (Code::FileTooShort), after what it had was sent. On bare metal (EPYC 4345P, Linux 7.0, one server core) giong-http serves a 1 MiB file over HTTPS at 6,104 req/s with kernel TLS and sendfile against 4,484 with rustls (+36%; nginx with kernel TLS and sendfile: 6,039). With 64 KiB files, from memory and for small responses kernel TLS is 4–22% slower than rustls, so Ktls::Off stays the default; the giong-tls README has the table and when to turn it on. Recorded in bench/results/bare-metal-epyc-4345p/linux-7.0/ktls/.
  • giong-tls: TlsStream::write_all_vectored(bufs) sends several buffers, a header and a body for example, without copying them into one first. giong-http uses it for bodies of 32 KiB or more over HTTPS, which it used to copy after the head.
  • giong: on Linux 6.2 and newer, TCP sends of 16 KiB and more from bytes that cannot change (&'static [u8], Rc<[u8]>, Arc<[u8]>, so giong-http's static bodies) go out without a copy into the kernel (IORING_OP_SEND_ZC, zero-copy-send): the network card reads them, and the write still returns as soon as they are queued, so a writer is never held to the peer's acknowledgements. A vectored write may add up to 4 KiB from other buffers (an HTTP head), which are copied aside. Bytes that can change once the write returns (a Vec) are copied as before. A socket goes back to plain sends for good when the kernel reports that it copied the data anyway (loopback, a card without scatter-gather) or cannot send this way (kTLS); Unix sockets never use it. On bare metal (Linux 7.0, 25 GbE) it cuts the CPU time per request by 16% at 64 KiB, 62% at 256 KiB, 68 to 72% at 1 MiB and 85 to 86% at 16 MiB across runs, at the same request rate. bench/uring-features.sh measures each optional io_uring feature against the rest, on one machine or two.
  • giong: DriverChoice::io_uring_features lists the optional io_uring features a worker uses (giong::IoUringFeature), and its one-line form names them (io_uring (chosen automatically), using packed-buffers). Each is probed when a worker starts and skipped where the kernel lacks it. GIONG_IO_URING_OFF (names, or all) turns them off for tests and benchmarks, as GIONG_RING_TIER does for the ring setup.
  • giong: TcpStream::poll_recv and UnixStream::poll_recv, the poll form of recv, for futures written by hand and for adapters such as giong-compat.
  • giong: TcpStream::send_with_control(buf, control), one sendmsg with ancillary data, on both drivers (giong-tls sends TLS alerts and key updates through it).
  • giong-compat, a new crate: Compat gives giong's TcpStream, UnixStream and (with the tls feature) giong-tls's TlsStream the AsyncRead, AsyncWrite and AsyncBufRead traits of tokio::io and of futures_io, so that crates generic over their transport run on giong with no Tokio runtime: tested with tokio-rustls, futures-rustls, tokio-tungstenite, h2 (also over giong-tls with ALPN), hyper's HTTP/1 connection API (against giong-http both ways) and tokio-util's codecs, on io_uring and epoll. Writes are buffered like BufWriter (64 KiB by default) and sent on flush, when the buffer is full or when a read waits; a partly read chunk never holds the worker's receive pool; TCP_NODELAY is turned on. It costs a copy each way (none for reads through AsyncBufRead), measured by bench/compat.sh in four sessions (sending 10–20% slower, receiving with read 6–13% more CPU per byte). Errors GIONG-E1401 (an earlier buffered write failed), E1402 (write after shutdown) and E1403 (invalid setting). A hyper server over Compat needs a hyper::rt::Timer for its header timeout; the README shows one built on giong's timers.
  • Verification: two new fuzz targets in the nightly fuzz workflow, hpack (header blocks decoded, encoded again and compared; Huffman both ways) and h2 (whole connections from a client that follows the protocol mostly, every frame the server writes checked against RFC 9113 and the client's flow control). The same checks run in cargo test (100,000 header blocks and 3,000 connections a run).
  • Verification: a fuzz target for the client's side of HTTP/2, h2_client: frames a server might send, fed in pieces while requests come and go, with checks that the client holds no more than the windows it grants and writes only well-formed frames within the server's windows. 3,000 such connections run in cargo test.
  • Verification: KTLS=1 scripts/kernels.sh 6.1.155 6.18.63 loads the kernel's tls module in the QEMU guest (from Ubuntu's modules package) and requires the kernel TLS tests to run there (GIONG_KTLS_REQUIRED=1); CI does this on 5.15 (epoll), 6.1, Ubuntu's 6.8 and 6.18, and loads the module on its runners for the test, fallback, tsan and docker jobs.
  • Verification: scripts/check.sh fallback (and CI's fallback job) also runs the suite with the optional features off, and the QEMU kernels include 6.12, the first with packed buffer rings; every QEMU run checks which features giong found.
  • Benchmarks: bench/tls.sh adds giong-http-ktls (giong-http with Ktls::Required), 64 KiB and 1 MiB responses from memory (bytes64k, bytes1m) and from a file (file64k, file1m, file64k-open), the server's CPU time per request and an error count; SERVERS and ENDPOINTS pick a subset. bench/http-client.sh adds a giong client with kernel TLS and the same body sizes.

Changed

  • giong: on Linux 5.18 and newer, a worker enters io_uring through its thread's registered ring table (IORING_REGISTER_RING_FDS) instead of the ring's descriptor, so the kernel no longer looks the descriptor up on each io_uring_enter (about 11 of the 130 ns an enter costs). DriverChoice lists it as registered-ring.
  • giong: on Linux 6.12 and newer, stream receives fill the worker's pool buffers piece by piece (a buffer ring with IOU_PBUF_RING_INC) instead of taking a whole 8 KiB buffer each, so connections that each send a little share a few buffers. With 20 workers and 5,000 busy connections, giong-http's peak memory fell from 50 to 23 MiB (epoll: 15 MiB); requests per second did not change. Datagrams still take whole buffers. A stream's data can now be cut where a buffer fills, so one write by the peer may come back from recv in two pieces; streams never promised otherwise.
  • giong: a stream that receives a lot at once (a bulk transfer, a large upload) is no longer copied out of the pool on io_uring. More than 8 receives for one stream between two turns of the event loop used to count as a reader falling behind: the rest was copied to the heap and the receive paused, which on a 256 KiB-at-a-time transfer copied 9 bytes in 10. The limit is now an eighth of the pool (64 receives by default), and only data its reader left unread for a whole turn is copied, while the pool runs low or is empty. Receiving such a transfer on loopback now costs the worker 167 instead of 565 ns of CPU per KiB (epoll: 169), at 3.0 instead of 1.6 GiB/s. On kernels before 6.1 (no DEFER_TASKRUN), where one fast stream can fill the whole pool in a single turn, the cost falls by a third to a half (measured on 6.18 with the ring setups giong uses on 5.19 and 6.0, then on 5.15: 171 instead of 253 ns per KiB, 184 instead of 338).

Fixed

  • giong: Linux 6.14 to 7.2 count every io_uring ring against the locked-memory limit (RLIMIT_MEMLOCK) of a process without CAP_IPC_LOCK, summed over the user's processes (7.3 stopped, and so did 6.18 from 6.18.58): about 150 KiB per giong worker, so the common 8 MiB limit holds about fifty workers. Past it, a worker whose rings did not fit failed with a bare Cannot allocate memory, which stopped the runtime, and one whose buffer ring did not fit fell back to epoll blaming the kernel (GIONG-E0009, "may be a kernel bug"). Such a worker now runs on epoll, unless io_uring was asked for, and the error is the new GIONG-E0010 (Code::LockedMemoryLimit), which names the limit and how to raise it; DEPLOYMENT.md has the settings for systemd, Docker and Kubernetes. CI's runners have 7.0 kernels and a limit, which a test running several runtimes at once went past; CI now lifts the limit there, so that the suite runs on io_uring every time, and a test sets it to nothing to check the fallback.
  • giong: on Linux 6.0 and 6.1, io_uring gives up waiting on a non-blocking socket when a woken sendmsg or recvmsg still cannot proceed (it retries on a kernel thread, which then sees O_NONBLOCK) and completes with EAGAIN. giong now submits such an operation again instead of returning WouldBlock. Sockets were blocking under io_uring until send_file, which needs O_NONBLOCK; a test with four writers on one small buffer failed on both kernels without the fix.
  • giong: a UdpSocket bound to port 0 could get a port that another UDP socket of the same user already held, in this process or another, and the two sockets then split each other's datagrams by a hash of the sender's address: answers went to the wrong socket and the one waiting for them never saw them. With SO_REUSEADDR or SO_REUSEPORT set, Linux picks a port for port 0 without avoiding the sockets that hold one with the same options; of 1,000 sockets bound to 127.0.0.1:0 at once, about 15 pairs shared a port. UdpSocket::bind now sets neither option for port 0, so such a socket has its port to itself (binding that port again fails with AddrInUse); sockets bound to a port given explicitly share it between workers as before. This was the rare UDP failure in 0.4.0's CI. TCP listeners were not affected.
  • giong, ThreadSanitizer builds only (--cfg giong_tsan): a socket or file closed with close(2) could still have operations queued in the ring, and a socket that got the same descriptor number next could have its data taken by them. Queued operations now go to the kernel before the close.
  • Tests: tests that took a port from a socket closed at once, to connect where nothing listens or to share it between workers, now hold it with a socket that is bound but does not listen, so a test running alongside cannot take it in between. The load-balancing test judges the hand-over rule with exact load figures instead of timing (no worker more than two connections ahead, every run); the burst of connections is still run, and its spread printed, not judged.

Foundations for services

November 13, 2026 · GitHub release · every commit

Foundations for services, and a look inside them. giong now runs where io_uring is blocked or missing (Docker and Kubernetes with their default seccomp profiles, gVisor, kernels before 6.0) on an epoll driver it falls back to by itself, about as fast as Tokio there, and it says when and why it does. On Ubuntu 24.04's own 6.8 kernels, whose backported bug rejects every io_uring buffer ring, it now runs on io_uring at full speed. giong-http streams bodies both ways, giong-web gains tracing, and an example REST API built only on giong's crates (PostgreSQL, Redis, HTTPS) serves 1.5 to 2.1 times as many requests per second as the same API on axum. The new giong-mcp lets an AI agent look inside a running service and names the task that blocks a worker. An idle connection now costs 1.9 KiB instead of 10.9 (axum 20.4, Go 18.9), and new work is balanced across workers when it is placed. Two changes in giong-http break code that used it: Body is #[non_exhaustive], and a closure passed to Server::serve needs its argument's type written.

Added

  • giong: giong::driver_choice() (on a worker) and Handle::driver_choice(worker) (from any thread) say which driver a worker runs on, whether Builder::driver, GIONG_DRIVER or giong chose it, why io_uring is not used when giong fell back to epoll (the full GIONG-E… error), and which kernel bugs giong works around. Falling back to epoll by itself is also said once per process on stderr, with the reason; naming a driver chooses without it. giong-mcp's overview shows the choice for each worker and warns when workers fell back to epoll.
  • Verification: CI's test, fallback and tsan jobs fail if giong would not choose io_uring by itself on the runner (GIONG_TEST_EXPECT_DRIVER=io_uring), instead of quietly testing epoll only, and the whole suite also runs on Ubuntu 24.04's own kernel (6.8.0-147) in QEMU: scripts/kernels.sh ubuntu-6.8.0-147 boots any kernel Ubuntu ships. Every QEMU run checks the driver giong chose and the kernel bugs it worked around.
  • An epoll driver, so that giong runs where io_uring is blocked or missing: in a Docker container with the default seccomp profile, in Kubernetes with RuntimeDefault, under gVisor, with the kernel.io_uring_disabled sysctl, and on kernels older than 6.0 (tested on 5.15). A worker falls back to it by itself when io_uring cannot be set up; Builder::driver(DriverKind::IoUring | DriverKind::Epoll) or GIONG_DRIVER=io_uring|epoll choose explicitly (asking for io_uring where it is blocked fails with GIONG-E0001, as before), and giong::driver_kind() tells which driver a worker got. Every API behaves the same on both; on epoll, file operations run on a pool of blocking threads, except on pipes and sockets, and a file is closed only once the threads are done with it. On one core, epoll does what raw Tokio and a hand-written epoll server do (158k requests per second on a small response at 50 connections, 2.02 system calls per request), while io_uring keeps its lead where batching counts: 55.7k against 32.7k requests per second on an 8 KB response. The README has the full comparison.
  • Verification: scripts/check.sh fallback also runs the suite on epoll; scripts/check.sh seccomp runs it with io_uring blocked the way Docker blocks it (scripts/no-io-uring.py), and CI runs it inside a Docker container with the default profile and on a real 5.15 kernel. ThreadSanitizer runs on both drivers.
  • giong-mcp, a new crate: an MCP server that lets an AI agent look inside a running service. Started with GIONG_MCP=127.0.0.1:7777 (or Config::tcp/Config::unix in code), it listens only on loopback or a Unix socket (GIONG-E1301 otherwise), refuses requests whose Host or Origin is not local, and takes an optional bearer token. Five read-only tools: overview (process, workers, warnings), workers, tasks (live tasks by the line that spawned them), sources (connection pools) and profile (where the workers spend their time over a window). It runs on a thread of its own, so it answers when every worker is stuck, and names the task a blocked worker is in.
  • giong: giong::observe, what giong-mcp reads. Handle::pulse(worker) returns a worker's counters (event-loop turns, polls, sleeps, idle time, spawned tasks) and the task it is polling, from any thread, without disturbing it. spawn, Handle::spawn_on and Handle::spawn_balanced record the line that called them, and observe::snapshot() groups a worker's live tasks by it, with its timers, I/O in flight, receive buffers and registered Sources. Handle::set_profiling and observe::take_profile() time task polls by spawn location. The counters cost about nine instructions per task poll (callgrind, tasks that only yield); profiling, while off, one load per batch of tasks.
  • giong-postgres, giong-mysql, giong-redis: pools register themselves as giong::observe sources (server and database, never credentials), so giong-mcp shows their connections, waiters and errors.
  • Streaming bodies in giong-http's server, both ways, with backpressure.
    • Request bodies read as they arrive: a handler whose Handler::stream_body(&req) returns Some(limit) is called once the head is in, and reads the body with req.body_stream() (BodyStream::chunk, read_to_end), one piece in flight at a time. Nothing is read until the handler asks, so it can refuse an upload before the client sends it (100 Continue only then). Content-Length and chunked bodies are both streamed; a body announced past the limit gets 413 without calling the handler, one that grows past it fails with GIONG-E1111; a client that closes or stalls (each piece gets request_timeout, the whole body no deadline) gives GIONG-E1112, broken chunked framing GIONG-E1113. A handler that answers before the end of the body gets its response sent, then the connection closes.
    • Response bodies written as they are produced: Body::channel() gives a BodySender and a Body for the response. The head goes out when the handler returns, each piece as soon as it is sent, with Transfer-Encoding: chunked (to an HTTP/1.0 client without a length, then the connection closes). send waits until the previous piece is written; it fails with GIONG-E1114 once the client is gone or the response has no body (HEAD, 204, 304). BodySender::abort ends the body without its last chunk, so the client sees it is incomplete. Large pieces are written without a copy, as large bodies are.
    • The connection fuzz target streams request and response bodies too.
  • giong-web: streaming and tracing.
    • Router::stream_bodies(max): the routes of that router (wherever it is nested) read their body as it arrives, with Req::body_stream(), up to max bytes. ? on a body error answers 413 (GIONG-E1111) or 400 (GIONG-E1112, E1113); Req::json on such a route is a 500 whose logged cause says to use the stream. Timeout leaves these requests alone, Compression leaves streamed responses alone, and Logger writes "bytes":null for them.
    • middleware::Trace, behind the new tracing feature: each request runs in a request span (target giong_web) with OpenTelemetry's field names (http.request.method, url.path, http.route, http.response.status_code, client.address) plus request_id and worker, so events the handler records carry them; the span ends with one event, at ERROR with the code and cause for a 5xx.
    • 4 new error codes, GIONG-E1111 to E1114; 87 in all.
  • examples/rest-api, a complete REST API on giong's own crates: users in PostgreSQL (giong-postgres), read through a Redis cache (giong-redis), served over HTTPS (giong-tls) by giong-web, with create, read, update, delete, keyset pages and an NDJSON export streamed with Body::channel. Each worker has its own pools and listener. Its test starts a throwaway PostgreSQL and Redis and goes through every route, including reads with the cache down. bench/rest-api.sh measures it against the same API on axum 0.8 (bench/rest-api-axum), one worker each over HTTPS: 69.9k against 47.2k requests per second on cached reads, 35.9k against 19.5k on pages from PostgreSQL, 54.1k against 25.8k on inserts (medians of 5 rounds; method and ranges in the example's README).
  • Load balancing across workers, without moving a task once it has started (so tasks still need not be Send):
    • Handle::spawn_balanced(f): f waits in a queue shared by the workers, and the first worker with nothing else to run takes it; busy workers also take one now and then, so no job waits for ever. 64 jobs of uneven CPU cost started from one worker finish in 5.7 ms on 4 workers (median of 15 rounds), against 6.9 ms placed round-robin and 16.8 ms on the worker that started them; the slowest round took 6.5, 10.4 and 19.7 ms (bench/spawn-balanced).
    • TcpListener::bind_balanced(addr): listeners of the same runtime on the same address form a group, and a worker that looks clearly busier than another member hands each new connection it accepts to that member. SO_REUSEPORT alone spreads connections by a hash of their addresses, so with 6 connections on 3 workers running a CPU-heavy route the result depends on where the hash puts them: over 10 runs plain listeners gave 37,000 to 54,000 requests per second (median 51,600, p99 448 µs), balanced ones 47,000 to 59,000 (median 53,000, p99 408 µs) (bench/balance.sh).
    • Handle::least_loaded_worker(), from hints each worker publishes between batches of tasks (live tasks, runnable tasks, asleep or not), plus work sent to a worker that it has not taken in yet. Publishing them costs about 0.1% of the instructions per request of a small HTTP response.
  • giong-web, a new crate: routing, middleware and JSON for HTTP services on giong-http.
    • A handler is an async fn(Req<S>) -> Result<Response, Error>, and ? works on any error. Router::new().get("/users/{id}", user).nest("/teams/{team}", members) .layer(m).build(state) builds an App per worker, with no locks and nothing Send. Patterns have parameters ({id}) and a catch-all ({*path}); a literal segment wins over a parameter, a parameter over a catch-all, with backtracking. HEAD is answered by the GET route, OPTIONS and 405 with Allow are answered for every path, and a 404 for /users/ names /users when that exists.
    • req.param::<u64>("id")? and req.query_param::<u32>("page")? parse into any FromStr type: a value that does not parse is a 400 (GIONG-E1205) naming the parameter and the expected type, and asking for a parameter the route lacks is a 500 (GIONG-E1206) whose cause names the route. With the serde feature, req.json::<T>() (415, 400 or 422: GIONG-E1208, E1207), req.query::<T>() and json(status, &value).
    • Every error answer is an RFC 9457 problem+json body with a stable code ({"status": 404,"code":"GIONG-E1203","title":"Not Found","detail":"no route for GET /x"}), and the request id when there is one. Error::bad_request(code, detail) and its siblings make one with your own code; an error that is not one becomes a 500 (GIONG-E1210) whose cause is logged and never sent, or a 503 with Retry-After (GIONG-E1211) when it is a giong error for a database or service that cannot be reached. A 5xx no Logger reported goes to stderr. Two routes for the same requests, or an invalid pattern, panic at startup with a code and the line that added them.
    • Middleware is a trait with one async fn call(&self, req, next); they run in the order added, and those of a nested router only for its routes. Changed

  • An idle keep-alive connection to giong-http costs 1.9 KiB instead of 10.9 KiB, and one whose request is being handled 7.2 instead of 15.0 (Axum: 20.4 and 19.3, Go's net/http: 18.9 and 18.3; 10,000 connections, bench/memory.sh). The connection's task was most of it: every wrapper that took a future by value kept two copies of it (the task around a spawned future, time::timeout, until_shutdown, the connection limit, Conn::run), so a 2.3 KB connection future took a 9.2 KB task. And the handler's future lived inside the connection's, so every idle connection was as large as the largest future the handler can make: one that held 8 KiB across an .await made each idle connection cost 43 KiB, 430 MB for 10,000. Now the handler's future is on the heap only while a request is handled, in blocks the worker reuses. With 20 workers and 5,000 busy connections the server peaks 50 MiB above its idle memory instead of 120 (raw Tokio: 64 MiB, Axum: 124 MiB, Go: 184 MiB; 14 MiB on epoll). Throughput is unchanged within noise (7 interleaved rounds of /json at 100 and 1,000 connections); callgrind counts 2% more instructions per request in user space.
  • giong: time::timeout returns a time::Timeout<F> and until_shutdown a giong::UntilShutdown<F>, each only as large as the future it wraps plus a timer or a shutdown signal, instead of an async fn's future twice that size. Awaiting them is unchanged. A spawned task is as large as its future, no longer twice.
  • giong: a worker lends the kernel 16 receive buffers at first, and twice as many each time a turn of the event loop takes most of them, instead of all 512 at once; free buffers are reused most recent first, on both drivers. The kernel takes the buffers of its ring in turn, so with all of them lent every buffer was touched sooner or later and the whole pool became resident, 2 to 4 MiB per worker however light the traffic: with 20 workers and 100 busy connections, giong-http's memory rose by 40 MiB, now by 1 MiB.
  • giong-http: a connection hands its read buffer back before its responses are sent rather than after, so on io_uring, where a buffer stays with the kernel until the send completes, the connections of one turn share fewer buffers. The buffers a worker keeps for connections to reuse are bounded at 4 MiB, and one that grew past 16 KiB is freed rather than kept. Before, up to 1,024 of up to 256 KiB each could stay, and a large one could be handed to a small request and held for as long as its handler ran.
  • giong-http: Server::serve_connection returns its future instead of being an async fn; the future no longer borrows the Server.
  • giong: a runtime that cannot use io_uring now starts on epoll instead of failing with GIONG-E0001 or GIONG-E0002; those errors are raised only when io_uring was asked for. An unknown GIONG_DRIVER value fails with GIONG-E0004. docs/DEPLOYMENT.md explains when each driver is used.
  • Breaking: giong-http: Body is #[non_exhaustive] and has a new variant, Body::Stream; a match on it needs a _ arm. Body::as_bytes and len are empty for a stream, and is_empty is false (Body::is_stream, Response::is_streaming tell). Server::max_body_size does not apply to bodies read as a stream.
  • Breaking: giong-http: Server::serve, serve_unix and serve_tls take any Handler. A closure passed to them needs its argument's type written (|req: Request| async move { .. }): Rust no longer infers it.
  • giong-http: the client asks for compressed responses and decodes them by default (see Added); a decoded response no longer has Content-Encoding and Content-Length among its headers. A request that sets Proxy-Authorization itself is refused (GIONG-E1101): the client sets it, for the proxy only.
  • giong-http: the client runs 41% fewer instructions per request (18,795 to 11,115 under callgrind, json). Each request's future held, unused, the future that opens a connection, TLS handshake included, and copied its 8 KB or so at every await; that future is now boxed and lives on the heap only while a connection opens. The response head is no longer copied out of the buffer it was read into either. On one core, requests per second rose by 3 to 16%, and with 64 connections the client sends 1.6 to 2.0 times as many as reqwest (bench/http-client.sh, median of 5 rounds).

Fixed

  • io_uring on Ubuntu 24.04's own kernels. Ubuntu's 6.8 kernels from 6.8.0-135 on (and the AWS, Azure, GCP and Oracle 6.8 kernels and the 6.8 HWE kernel of 22.04 built from them) refuse every correctly formed io_uring buffer ring: a backport of "io_uring/kbuf: use mem_is_zero()" inverted the check on its reserved fields, so the kernel rejects zeroed ones and accepts others. giong 0.3 would not start there, calling the kernel too old, and with the epoll driver alone it would have run on epoll without saying so. It now recognises the bug with a probe that changes nothing and registers its ring the way that kernel accepts, so io_uring runs at full speed; on correct kernels nothing changes. giong::driver_choice() lists it under kernel_workarounds (KernelWorkaround::BufferRingReservedCheck). Found on Ubuntu 24.04 bare-metal machines (6.8.0-147); checked on 6.8.0-134 (no bug), -135, -147 and -149.
  • A kernel from 6.0 on that refuses buffer rings for another reason is no longer called too old: the error is the new GIONG-E0009 and names the kernel release (GIONG-E0002 stays for kernels older than 6.0).
  • Tests: accept_many_connections and accept_backlog_is_bounded_and_no_connection_is_lost failed with "too many open files" under the 1024 soft limit that shells start with; they raise the soft limit up to the hard one.
  • giong-http server: more than two blank lines before a request line start the request timeout. A client sending \r\n once a minute kept a connection open for ever.
  • giong-http client: a kept-alive connection that received anything while idle (a 408 Request Timeout that some servers send before closing, the rest of a body longer than its Content-Length) is no longer used. The bytes were read as the response to the next request.
  • giong-http client: a Host header set by hand is not sent to another origin after a redirect, like Authorization and Cookie.
  • giong-http client: idle connections of an origin that is not asked for again are closed after the idle timeout, and the origin is forgotten. Before, they stayed open, with their entry, for as long as the client lived.
  • giong-postgres and giong-mysql: transactions no longer run on the connections a pool shares. Pool::query, query_one, query_opt and execute (and insert in giong-mysql) refuse BEGIN, START TRANSACTION, COMMIT, ROLLBACK, SAVEPOINT and the other transaction statements (MySQL also XA, LOCK and UNLOCK) before sending anything, with the new error codes GIONG-E3011 and GIONG-E3111 (ErrorKind::Statement). Before, pool.execute("BEGIN", &[]) left a connection that other tasks share inside a transaction: their statements ran in it and were never committed, though they had been told they succeeded. A Pool::batch_execute that leaves a transaction open (or, in MySQL, autocommit off) now closes its connection, which rolls the transaction back, and fails with ErrorKind::Closed, as do the statements pipelined behind it.
  • giong-postgres and giong-mysql: a PooledClient given back while a statement is still in flight (its future dropped by a timeout) queues a ROLLBACK first. If that statement was BEGIN, the connection went back to the shared pool inside a transaction, because the last answer still said there was none. giong-mysql closes a connection given back with autocommit off.
  • giong-postgres and giong-mysql: Pool::get waiting for a connection is woken when a statement whose future was dropped frees it. It waited out the wait timeout and failed with PoolTimeout.
  • giong-postgres: rows without columns (SELECT FROM t) are counted; query returned none.
  • giong-mysql: a TIME with more days than MySQL allows no longer overflows when it is read as text.
  • giong-redis: a watch cancelled while waiting for WATCH's reply sends UNWATCH. Before, the watch stayed on the connection, and once a pool shared it, another task's atomic pipeline could be skipped by EXEC while reporting success.
  • giong-redis: an atomic pipeline whose EXEC answers nil (a watched key changed, outside a Watch) is an error, "the transaction did not run", instead of a value.
  • giong-redis: a push message larger than Config::max_reply_size (a client-side caching invalidation) is passed over. Before, it was counted as the reply to the oldest command, and every later reply went to the wrong command. An attribute count out of range at the front of such a message (|9223372036854775807, or a negative one) is no longer multiplied: it overflowed, a panic in a debug build. Found by the replies fuzz target.
  • giong-redis: a task waiting in Pool::take is woken when a shared command whose future was dropped frees the connection. Before, it slept until the wait timeout and could fail with PoolTimeout while the connection was free.

Security

  • giong: localhost and names under .localhost resolve to the loopback addresses without asking DNS (RFC 6761). Before, they went through the search list first, so a wildcard record in a search domain, or a forged answer, could point localhost at another machine, which giong-postgres and giong-mysql then trusted as local: no TLS, the password sent in the clear, MySQL's RSA key fetched unverified. A hosts file entry for such a name is used only if it is a loopback address.
  • giong-http: chunk extensions are limited to 16 KiB per body, on the server and in the client. They counted toward no limit, so a peer could send about 4,000 bytes per byte of body, all of it held in memory until the body ended (the flaw of Node.js CVE-2024-22019). Such a request is answered with 400; such a response is an error.

Fixed

  • A wake-up from another thread could be lost, leaving the task asleep until something else woke it. The executor cleared a task's "queued" flag with a plain store before polling it; a waker that published new state and then saw the flag still set skipped the enqueue, while the poll could read the state from before the wake-up. It needs state that is shared without a lock (a Mutex hides it), and on x86 it hit about 70 in a million such wake-ups. The flag is now cleared with a swap, which synchronises with the waker.
  • On Linux 6.0 a runtime could fail to start with "giong needs io_uring buffer rings (Linux >= 6.0): Bad address", depending on what happened to be mapped next to the receive buffer ring: 6.0 pins one page more than the ring needs (fixed in 6.1). The ring now has a spare page. Found by running the tests on a real 6.0 kernel.

Security

  • A security review of giong-tls and of every crate that uses it found two issues in code that is new in this release, both fixed before it shipped:
    • The giong-http client accepted an HTTPS response body that ends where the connection ends (no Content-Length, not chunked) when the TCP connection closed without a TLS close_notify, so someone on the path could cut it short. Such a response is now an error (GIONG-E1106).
    • giong-mysql kept part of a packet received after the plaintext greeting and read it after the TLS handshake as if it had come through TLS, so someone on the path could slip bytes into the encrypted session (the flaw of CVE-2021-23222 in PostgreSQL clients). Any byte left over before the handshake now ends the connection.

Known limitations

  • Not run in production yet.
  • The multi-core benchmark ran under WSL2 over loopback; scaling on bare metal and a physical network are not measured.
  • The giong-tls review was done by the project's AI agent; an independent review is still wanted.
  • No HTTP/2, no streaming HTTP bodies, and tasks do not move between workers.

0.2.0

A runtime you can serve from

November 12, 2026 · GitHub release · every commit

giong becomes a workspace of three crates: the runtime, an HTTP/1.1 server library and TLS. The runtime gains graceful draining, Unix sockets, multishot UDP and the rest of the file operations, and is now checked under ThreadSanitizer and on the io_uring setups of older kernels.

Show the 14 changes in 0.2.0

Added

  • giong-http (new crate): a small, strict HTTP/1.1 server. One async handler; bodies by Content-Length or chunked; keep-alive and pipelining; limits on head and body size; timeouts for idle connections, slow requests and slow readers; graceful shutdown. Requests a proxy in front could read differently (two Content-Length headers, Content-Length with Transfer-Encoding, bare LF, folded headers) are refused with 400. Server::serve for TCP, Server::serve_unix for Unix sockets, Server::serve_tls for HTTPS behind the tls feature, and the Transport trait with Server::serve_connection for anything else.
  • giong-tls (new crate): server-side TLS 1.2 and 1.3 on rustls with ring. TlsAcceptor and TlsStream; receiving is cancel safe, and a cancelled write poisons the sending side of the connection instead of corrupting the record stream.
  • Runtime
    • Builder::shutdown_grace: after a worker's main future returns, its remaining tasks get this long to finish the request they are working on. is_shutting_down() tells a task that it is time to stop taking new work.
    • GIONG_RING_TIER=coop|basic forces the io_uring setup used on kernels older than 6.1, so those paths can be tested on a new kernel.
  • Networking
    • UnixListener and UnixStream, with the same interface as their TCP counterparts, plus UnixStream::pair.
    • UdpSocket::recv_from and recv on multishot recvmsg with the provided buffer ring: cancel safe, one submission for the life of the socket, datagrams returned as a Datagram borrowed from the worker's pool (Datagram::is_truncated reports one that was longer than a pool buffer). UdpSocket::set_broadcast.
  • Files
    • File::metadata, fs::metadata and fs::symlink_metadata (statx), with Metadata (len, is_file, is_dir, is_symlink, mode, modified).
    • fs::read, fs::write, fs::rename, fs::remove_file, fs::remove_dir, fs::create_dir, and OpenOptions::custom_flags.
  • Verification
    • scripts/check.sh: the whole suite repeated in release mode, on all three io_uring setup tiers, and under ThreadSanitizer. CI runs all of it, plus a build with Rust 1.80.
    • Sanitizer builds (--cfg giong_tsan) close descriptors with close(2) instead of through the ring, which ThreadSanitizer cannot see and reported as races on reused descriptor numbers.
    • 169 tests across the three crates (87 in 0.1).
  • Benchmarks: giong-http in bench/run.sh; a two-core run; bench/tls.sh (HTTPS against Axum + rustls) and bench/fs.sh (file I/O against Tokio and blocking std). Every benchmark server now starts one worker per CPU it is allowed to run on.
  • Documentation: logo and brand assets in assets/; the README shows the logo for light and dark themes, and the API documentation uses the giong icon.

Changed

  • Breaking: UdpSocket::recv_from(buf) and recv(buf), which read into a buffer of the caller's, are now called read_from(buf) and read(buf), matching TcpStream::read. The names recv_from() and recv() now belong to the multishot, pool-buffer variants, matching TcpStream::recv. The two kinds must not be mixed on one socket: after recv_from, read_from fails with InvalidInput.
  • The benchmark's giong entry is bench/giong, the same program as the Monoio, Tokio and epoll servers; examples/http.rs is no longer measured. All recorded results were measured again on a 4-vCPU machine.

Known limitations

  • A one-off read that is dropped (TcpStream::read, UdpSocket::read_from, File::read_at on a pipe or device) can still take data. Use recv and recv_from where a read has to be cancel safe.
  • No real 6.0 kernel was available: the fallback setups are exercised by forcing them on 6.18.
  • giong-tls has no client side and has not had an independent security audit; the cryptography and the protocol are rustls's.
  • Still no asynchronous DNS, no HTTP/2 and no streaming HTTP bodies.

0.1.0

Foundation

November 11, 2026 · GitHub release · every commit

First release: a thread-per-core async runtime for Linux on io_uring, with TCP, UDP, files, timers and cross-thread messaging. Not production-tested; see the limitations in the README.

Show the 17 changes in 0.1.0

Added

  • Runtime
    • block_on for a single-threaded runtime; Builder / Runtime::run for one worker thread per CPU, each pinned to its core with its own io_uring, run queue, timers and receive buffer pool.
    • Handle (shutdown, is_shutdown, spawn_on, workers), handle(), worker_id().
    • Graceful shutdown: shutdown_signal(), until_shutdown(fut), and Builder::shutdown_on_signals for SIGINT / SIGTERM.
    • A panic in a worker's main future stops the runtime and is propagated to the caller.
    • Builder::spin_before_park: an opt-in busy-poll mode that trades CPU for latency. A worker watches its ring for a while before sleeping, so it reacts to a request without a wake-up from the kernel.
  • Tasks
    • spawn for !Send futures, JoinHandle (await, abort, is_finished), JoinError, yield_now.
    • A panic inside a task is caught and reported through its JoinHandle.
  • Networking
    • TcpListener (bind with SO_REUSEPORT, accept, from_std) on multishot accept.
    • TcpStream (connect, recv, read, write, write_all, shutdown, set_nodelay, peer_addr, local_addr, from_std).
    • recv uses multishot receive with a kernel-provided buffer ring and returns a RecvBuf borrowed from the worker's pool.
    • UdpSocket (bind, connect, send, recv, send_to, recv_from, from_std), IPv4 and IPv6.
    • Ownership-passing buffer traits IoBuf / IoBufMut, implemented for Vec<u8>, String, Box<[u8]>, Rc<[u8]>, Arc<[u8]>, &'static [u8] and &'static str.
  • Files
    • fs::File and fs::OpenOptions: open, positional read_at / write_at / write_all_at, sync_all, sync_data, close. Every operation goes through the ring; there is no blocking thread pool.
  • Time
    • sleep, sleep_until, timeout, backed by a six-level hierarchical timing wheel with 1 ms resolution. Timers never fire early.
  • Sync
    • sync::mpsc unbounded channel, usable across workers and from threads outside the runtime.
  • Safety and backpressure
    • Cancellation safety: when an in-flight operation's future is dropped, its buffer is kept alive by the driver until the kernel confirms the cancellation.
    • recv and accept are cancel safe: wrapping them in timeout loses no data and no connection.
    • A slow or stalled reader cannot starve other connections: its multishot receive is paused and its backlog is moved off the shared pool.
    • A multishot accept pauses once 1024 accepted connections are waiting.
    • On shutdown every operation is cancelled and awaited before memory is released.
  • Examples: echo, http (HTTP/1.1 with keep-alive, pipelining, idle and write timeouts, size limits), udp_echo and cat.
  • Benchmarks: bench/run.sh (throughput), bench/scale.sh (one connection to thousands, with CPU time per request) and bench/syscalls.sh, with seven reference servers (Node.js, Bun, Axum, raw Tokio, hand-written epoll, Monoio, Glommio) and the recorded results.
  • Tests: 62 tests covering the executor, timers, TCP, cancellation, buffer exhaustion and multi-worker behaviour; scripts/valgrind.sh for a memcheck pass.

Known limitations

  • No Unix sockets and no asynchronous DNS (bind and connect resolve names blocking).
  • No TLS and no HTTP/2.
  • Not compatible with crates that require the Tokio runtime.
  • Tasks never migrate between workers.
  • Shutdown drops remaining connections; it does not wait for requests in progress.
  • Not yet measured on more than one core or on a physical network.
  • The declared minimum Rust version (1.80) and the fallback paths for kernel 6.0 have not been exercised yet.
