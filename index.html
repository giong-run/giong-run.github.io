One syscall per tick, not per operation.

giong is an async runtime for Rust services on Linux, built on io_uring with one thread per core, and an epoll driver wherever io_uring is blocked. It brings its own HTTP server and client, TLS, PostgreSQL, MySQL and Redis clients and a web framework, so a whole service runs on it with no Tokio underneath.

why giong

Built around the kernel's own queue

giong commits to io_uring and to one thread per core, and to nothing else. These are the six things that buys.

io_uring_enter · DEFER_TASKRUN

One syscall per tick

Every read, write, accept, close and cancellation a turn of the loop produces enters the kernel together, and every ready completion comes back in the same call. A request costs about 0.03 system calls; an epoll-based server needs 2.

multishot recv · provided buffers

Idle connections hold no buffer

One submission lasts the life of a connection. The kernel picks a buffer only when data arrives, so it is still warm in cache. At 5,000 connections giong spends the least CPU per request of the runtimes measured.

tests/cancel.rs

Cancel safe by construction

Drop an I/O future mid-flight and its buffer moves to the driver until the kernel confirms the cancel. A timeout around recv, recv_from or accept loses no data.

!Send · Rc · RefCell

Shared nothing

One thread per core, and a task never changes thread. Futures need not be Send; Rc and RefCell just work. No locks on the hot path.

giong::fs

Files on the same ring

Open, read, write, fsync, statx and rename are entries in the worker's ring, next to the network. No pool of blocking threads.

Builder::spin_before_park

A latency dial

Let a worker watch its ring before it sleeps: 19 µs median instead of 28 on one connection. It costs CPU, so it is off by default.

code

What the code looks like

Plain async fns and a builder. No macros. Every worker binds its own listener on the same port and the kernel spreads connections across cores.

REST API · giong-web

use giong::net::TcpListener;
use giong_web::middleware::{Logger, RequestId};
use giong_web::{json, Error, Req, Response, Router, Server, Sink};
use serde::Serialize;

#[derive(Serialize)]
struct User { id: u64, name: String }

async fn get_user(req: Req<()>) -> Result<Response, Error> {
    let id: u64 = req.param("id")?;   // "abc" is a 400 that names `id`
    if id == 0 {
        return Err(Error::not_found("user_not_found", format!("no user {id}")));
    }
    json(200, &User { id, name: "Ada".into() })
}

fn main() -> std::io::Result<()> {
    giong::Builder::new()
        .shutdown_on_signals(true)
        .build()?
        .run(|_worker| async {
            let app = Router::new()
                .get("/users/{id}", get_user)
                .layer(RequestId::new())
                .layer(Logger::new(Sink::Stdout))
                .build(());
            let listener = TcpListener::bind("0.0.0.0:8080").expect("bind");
            Server::new().serve(listener, app).await;
        })
}

Each worker builds its own app. A bad id is a 400 that names the parameter, as problem+json with a GIONG-E code.

HTTP server · giong-http

use std::time::Duration;
use giong::net::TcpListener;
use giong_http::{Request, Response, Server};

async fn handler(req: Request) -> Response {
    match (req.method(), req.path()) {
        ("GET", "/health") => Response::text("ok"),
        ("POST", "/echo") => Response::new(200).body(req.body().to_vec()),
        _ => Response::new(404),
    }
}

fn main() -> std::io::Result<()> {
    giong::Builder::new()
        .shutdown_on_signals(true)                  // Ctrl-C / SIGTERM stop it gracefully
        .shutdown_grace(Duration::from_secs(10))    // requests in progress are answered
        .build()?
        .run(|_worker| async {
            let listener = TcpListener::bind("0.0.0.0:8080").expect("bind");
            Server::new().serve(listener, handler).await;
        })
}

One SO_REUSEPORT listener per worker; requests in progress are answered before a worker stops.

PostgreSQL · giong-postgres

use giong_postgres::{Client, Config};

fn main() -> Result<(), giong_postgres::Error> {
    let config = Config::from_url("postgres://app:secret@localhost/shop")?;
    giong::block_on(async {
        let client = Client::connect(&config).await?;
        let rows = client
            .query("SELECT id, name FROM products WHERE price < $1", &[&100i32])
            .await?;
        for row in &rows {
            let id: i64 = row.get("id")?;
            let name: &str = row.get("name")?;
            println!("{id} {name}");
        }
        Ok(())
    })
}

Statements are prepared once per connection and cached. A Pool per worker pipelines the statements of every task.

Bare runtime · giong

use giong::net::TcpListener;

fn main() -> std::io::Result<()> {
    giong::Builder::new()
        .shutdown_on_signals(true)
        .build()?
        .run(|_worker| async {
            let listener = TcpListener::bind("0.0.0.0:8080").expect("bind");
            while let Some(Ok(stream)) = giong::until_shutdown(listener.accept()).await {
                giong::spawn(async move {
                    loop {
                        let Ok(data) = stream.recv().await else { return };
                        if data.is_empty() { return }       // peer closed
                        let reply = data.to_vec();
                        drop(data);                          // buffer back to the pool
                        if stream.write_all(reply).await.0.is_err() { return }
                    }
                });
            }
        })
}

recv() lends a buffer from the worker's pool; an empty buffer means the peer closed. Buffers go to the kernel by value and come back with the result.

agent-first

Made for the agents that write your code

More code is written by AI coding agents every month. giong is built so they get it right on the first try, and can fix it alone when they do not.

AGENTS.mdhow to build, test and change giong llms.txtwhere a model finds the docs 101 error codeseach with a page: cause and fix

  1. Errors that say how to fix them

    Every error giong raises has a stable code, the cause and the fix, and a page of its own. giong::error::code(&err) matches on the code, never on the message.

  2. One obvious way

    No macros that hide control flow. Strict types, so a mistake is a compile error. Every timeout and size limit is finite and documented.

  3. Verification is the law

    Tests, ThreadSanitizer, loom, fuzzing and soak tests run in CI and block merging. Machines check the work, not only reviewers.

  4. Docs a machine can read

    AGENTS.md in the repository and llms.txt on this site. giong-mcp lets an agent look inside a running service.

status

Where giong stands

Version 0.4 is complete enough to write real services, and it is checked hard. It is also young, Linux only, and narrow on purpose.

When giong is the wrong choice →

Checked

  • Tests repeated in release mode on all three io_uring setups and on epoll
  • Real Linux 5.15, 6.0, 6.1 and Ubuntu 24.04 kernels in QEMU, and Docker's default profile, on every change
  • ThreadSanitizer: no data race
  • loom model check of the cross-thread wake-up
  • Parsers fuzzed every night; a two-hour soak test
  • valgrind memcheck: no invalid access, no leak

Not yet

  • giong has not run in production
  • No bare-metal scaling numbers: the multi-core run was under WSL2, over loopback
  • giong-tls has had no independent security audit, only a review by the project's AI agent
