Get started with giong

Requirements, a first server, and every page of the documentation: a page for each crate, the best practices, the agent skill. The API reference for each crate is on docs.rs.

Requirements

linux
Production. io_uring on 6.0 or newer, 6.1+ recommended; developed and tested on 6.18. Elsewhere giong runs on its epoll driver, tested down to 5.15. Every crate.
macos
Development. A kqueue driver, tested on macOS 15 and 26 on Apple Silicon. Every crate; correct, not tuned.
windows
The runtime crate. I/O completion ports, tested on Windows Server 2022 and 2025: tasks, timers, channels, TCP, UDP, files, DNS. Unix sockets and the other crates come in later 1.x releases.
rust
1.80 or newer; 1.85 for giong-quic and giong-http's unstable-http3.
docker
Docker's default seccomp profile blocks io_uring, so giong runs on epoll there by itself. docs/DEPLOYMENT.md shows how to allow io_uring in Docker, Compose and Kubernetes without turning seccomp off.
license
MIT OR Apache-2.0, at your option.

Install

The crates are on crates.io and share one version number. Add the runtime and the layers you need; giong-http takes --features tls for HTTPS and --features client for its client.

cargo add giong
cargo add giong-web serde --features serde/derive   # routing, middleware, JSON

A first server

Put this in src/main.rs. Every worker binds its own SO_REUSEPORT listener on the same port, and the kernel spreads connections across cores.

use std::time::Duration;
use giong::net::TcpListener;
use giong_http::{Request, Response, Server};

async fn handler(req: Request) -> Response {
    match (req.method(), req.path()) {
        ("GET", "/health") => Response::text("ok"),
        ("POST", "/echo") => Response::new(200).body(req.body().to_vec()),
        _ => Response::new(404),
    }
}

fn main() -> std::io::Result<()> {
    giong::Builder::new()
        .shutdown_on_signals(true)                  // Ctrl-C / SIGTERM stop it gracefully
        .shutdown_grace(Duration::from_secs(10))    // requests in progress are answered
        .build()?
        .run(|_worker| async {
            let listener = TcpListener::bind("0.0.0.0:8080").expect("bind");
            Server::new().serve(listener, handler).await;
        })
}

Then run it:

cargo run --release          # listens on port 8080
curl localhost:8080/health   # ok

What happens to a request

One connection, from the kernel to your handler and back. Everything stays on the worker that accepted it, and every trip into the kernel that a turn of its loop needs, for all of its connections, goes in the same io_uring_enter.

Examples

Each one runs from a clone of the repository. examples/

examples/rest-api/

A whole service on giong-web: users kept in PostgreSQL, read through a Redis cache, served over HTTPS, with request ids, a JSON access log, readiness, a streamed export and graceful shutdown. Its README has the routes, the configuration and how it is tested.

cargo run --release -p rest-api

examples/echo.rs

A TCP echo server on every core.

cargo run --release --example echo
nc 127.0.0.1 7000

examples/http.rs

A small HTTP/1.1 server: keep-alive, pipelining, idle timeouts, a header size limit and graceful shutdown on SIGINT and SIGTERM. The same routes the benchmarks use.

cargo run --release --example http
curl localhost:3006/json

examples/udp_echo.rs

A UDP echo server, receiving with multishot recvmsg.

cargo run --release --example udp_echo
echo hello | nc -u -w1 127.0.0.1 7001

examples/cat.rs

Prints files to standard output, reading them through io_uring with positional reads.

cargo run --release --example cat -- Cargo.toml

examples/stdio.rs

A line protocol over standard input and output, as a local tool server speaks it: runs programs as child processes and answers with their output, and notes SIGHUP.

cargo run --release --example stdio
run uname -s

When giong is the wrong choice

Tuned for Linux

io_uring on 6.0 or newer, epoll elsewhere; on epoll giong is as fast as other epoll runtimes, not faster. macOS is for development, and Windows has the runtime crate only.

Not Tokio's ecosystem

Crates that need the Tokio runtime (sqlx, reqwest, tonic's transport) do not run on giong. Crates generic over a Tokio or futures-io stream (h2, tokio-rustls) run through giong-compat, at the cost of a copy.

TLS certificates

Certificates are not reloaded for you. Kernel TLS is off by default: it pays off for large files, not for data in memory.

Running tasks stay put

New work can go to the least busy worker (spawn_balanced, bind_balanced), but a task never moves once it has started.

Some gaps

Names come from /etc/hosts and DNS, not mDNS or LDAP. Also missing: Unix datagram sockets, multicast, file locks.

Pick something else when

Monoio is the mature choice and runs in production at ByteDance. If you need a runtime proven in production at scale today, use it.

Glommio is built for storage engines: Direct I/O and priority scheduling are its strengths.

Tokio is the default general-purpose runtime, with the largest ecosystem and years in production. giong aims to beat it on technical merit and replaces its crates with its own, but it has not run in production yet: measure your own workload before you switch.

Questions people ask

Is giong ready for production?

It is at 1.x with a frozen API, tested hard on every change and in long soaks, and one service runs on it so far, its author's. Measure your own workload before you switch, and read the limits on this page.

Does it run on macOS or Windows?

macOS, yes, for development: a kqueue driver runs every crate, tested on macOS 15 and 26 on Apple Silicon, correct but not tuned. Windows, the runtime crate: tasks, timers, channels, TCP, UDP and files on I/O completion ports, tested on Windows Server 2022 and 2025; the HTTP, TLS, database and other crates come to Windows in later 1.x releases. Until then use WSL2 or Docker for those.

Which Linux kernel do I need?

For io_uring, 6.0 or newer, 6.1 or newer recommended. giong tries three ring setups in order: DEFER_TASKRUN (6.1+), COOP_TASKRUN (6.0), then no flags. On an older kernel, or where io_uring is blocked, it runs on its epoll driver (tested on 5.15).

Can I use hyper, reqwest, sqlx or other Tokio crates?

Not crates that need the Tokio runtime; giong has its own HTTP, TLS, PostgreSQL, MySQL and Redis crates instead. Crates that only use std::future work, and crates generic over a Tokio or futures-io stream (h2, tokio-rustls, tokio-tungstenite, hyper's connection API) run through giong-compat.

Is it faster than Tokio?

Sometimes, and the benchmarks page says where. Small responses at 50 connections are a tie. giong makes about 0.03 system calls per request against 2.05, spends the least CPU per request at 5,000 connections, and reads files 8 times faster than Tokio on one core. On bare metal with 8 workers it served 2.45M requests/s against raw Tokio's 2.16M.

How do I report a security problem?

Privately, through GitHub's private vulnerability reporting (the Security link at the bottom of every page), not in a public issue.

Why the name?

After Thánh Gióng, the child of Vietnamese legend who lay silent for three years and then rose a giant: next to nothing while idle, every core the moment load arrives.
