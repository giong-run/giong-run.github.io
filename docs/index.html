Requirements

kernel
Linux. For io_uring, 6.0 or newer, 6.1+ recommended; developed and tested on 6.18. Elsewhere giong runs on its epoll driver, tested down to 5.15.
rust
1.80 or newer for the libraries.
elsewhere
giong does not build on Windows or macOS. Use WSL2 with a 6.x kernel or a Linux virtual machine.
docker
Docker's default seccomp profile blocks io_uring, so giong runs on epoll there. docs/DEPLOYMENT.md shows how to allow io_uring in Docker, Compose and Kubernetes without turning seccomp off.
license
MIT OR Apache-2.0, at your option.

Install

The crates are on crates.io. Add the runtime and the layers you need; giong-http takes --features tls for HTTPS and --features client for its client.

cargo add giong
cargo add giong-http          # or giong-web for routing, middleware and JSON

A first server

Put this in src/main.rs. Every worker binds its own SO_REUSEPORT listener on the same port, and the kernel spreads connections across cores.

use std::time::Duration;
use giong::net::TcpListener;
use giong_http::{Request, Response, Server};

async fn handler(req: Request) -> Response {
    match (req.method(), req.path()) {
        ("GET", "/health") => Response::text("ok"),
        ("POST", "/echo") => Response::new(200).body(req.body().to_vec()),
        _ => Response::new(404),
    }
}

fn main() -> std::io::Result<()> {
    giong::Builder::new()
        .shutdown_on_signals(true)                  // Ctrl-C / SIGTERM stop it gracefully
        .shutdown_grace(Duration::from_secs(10))    // requests in progress are answered
        .build()?
        .run(|_worker| async {
            let listener = TcpListener::bind("0.0.0.0:8080").expect("bind");
            Server::new().serve(listener, handler).await;
        })
}

Then run it:

cargo run --release          # listens on port 8080
curl localhost:8080/health   # ok

What happens to a request

One connection, from the kernel to your handler and back. Everything stays on the worker that accepted it, and every trip into the kernel that a turn of its loop needs, for all of its connections, goes in the same io_uring_enter.

Examples

Each one runs from a clone of the repository; the crates' READMEs have more. examples/

examples/echo.rs

A TCP echo server on every core.

cargo run --release --example echo
nc 127.0.0.1 7000

examples/http.rs

A small HTTP/1.1 server: keep-alive, pipelining, idle timeouts, a header size limit and graceful shutdown on SIGINT and SIGTERM. The same routes the benchmarks use.

cargo run --release --example http
curl localhost:3006/json

examples/udp_echo.rs

A UDP echo server, receiving with multishot recvmsg.

cargo run --release --example udp_echo
echo hello | nc -u -w1 127.0.0.1 7001

examples/cat.rs

Prints files to standard output, reading them through io_uring with positional reads.

cargo run --release --example cat -- Cargo.toml

When giong is the wrong choice

Linux only

io_uring on 6.0 or newer, epoll elsewhere. On epoll giong is as fast as other epoll runtimes, not faster. macOS and Windows are planned for after 1.0.

Not Tokio's ecosystem

Crates that need the Tokio runtime (hyper, sqlx, reqwest) do not run on giong. Crates that only use std::future do.

No HTTP/2

giong-http speaks HTTP/1.1. A request body over the limit is refused.

No kTLS

TLS runs in user space on rustls, and certificates are not reloaded for you.

Running tasks stay put

New work can go to the least busy worker (spawn_balanced, bind_balanced), but a task never moves once it has started.

Some gaps

Names come from /etc/hosts and DNS, not mDNS or LDAP. Also missing: Unix datagram sockets, multicast, file locks.

Pick something else when

Monoio is the mature choice and runs in production at ByteDance. If you need HTTP/2 or Tokio-compatible crates today, use it.

Glommio is built for storage engines: Direct I/O and priority scheduling are its strengths.

Tokio is the general-purpose runtime. giong is not trying to replace it for every workload.

Questions people ask

Is giong ready for production?

Not yet. It is complete enough to write real services and is tested hard, but it has not run in production. 1.0 waits for, among other things, at least one production user reporting back.

Does it run on macOS or Windows?

Not yet: both are planned for after 1.0, macOS for development and Windows for services that have to run there. Today, on Windows use WSL2 with a 6.x kernel (uname -r; wsl --update if it is older); on macOS a Linux virtual machine or Docker. In Docker giong runs on epoll; allow io_uring as docs/DEPLOYMENT.md shows to get its full speed.

Which Linux kernel do I need?

For io_uring, 6.0 or newer, 6.1 or newer recommended. giong tries three ring setups in order: DEFER_TASKRUN (6.1+), COOP_TASKRUN (6.0), then no flags. On an older kernel, or where io_uring is blocked, it runs on its epoll driver (tested on 5.15).

Can I use hyper, reqwest, sqlx or other Tokio crates?

Not crates that need the Tokio runtime; giong has its own HTTP, TLS, PostgreSQL, MySQL and Redis crates instead. Crates that only use std::future work. Adapters for the futures-io and Tokio I/O traits are on the roadmap.

Is it faster than Tokio?

Sometimes, and the benchmarks page says where. Small responses at 50 connections are a tie. giong makes about 0.03 system calls per request against 2.05, spends the least CPU per request at 5,000 connections, and reads files 5.5 times faster than Tokio on one core. Every number is over loopback on one machine.

How do I report a security problem?

Privately, through GitHub's private vulnerability reporting (the Security link at the bottom of every page), not in a public issue.

Why the name?

After Thánh Gióng, the child of Vietnamese legend who lay silent for three years and then rose a giant: next to nothing while idle, every core the moment load arrives.
