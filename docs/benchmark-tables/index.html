Method

Every server implements the same three routes (bench/): /json (a 27-byte body), /users (8 KB of JSON built per request) and /compute (a recursive Fibonacci). giong, Monoio, raw Tokio and the hand-written epoll server are deliberately the same program, with the same minimal HTTP parser, so they compare runtimes; giong-http is the library, with strict parsing, a Date header, timeouts and limits. Each server is pinned to its own core and wrk runs on another. Servers are measured in interleaved rounds and the tables show the median, with the range in parentheses. Machine, except for the runs under One worker to N: a 4-vCPU virtual machine (Xeon 2.1 GHz), Linux 6.18, Rust 1.97, Node 22, Bun 1.4, Tokio 1.54, Monoio 0.2.4, Glommio 0.9.0, wrk 4.1.

"Monoio (tuned)" is Monoio with DEFER_TASKRUN passed through uring_builder. Monoio's default ring has no such flag and is about 20% slower on the small response; comparing against the default would flatter giong.

  • giong, tuned Monoio, raw Tokio and epoll are within noise on /json. At this rate wrk is the bottleneck: in the syscalls.sh run below giong's core was busy 78% of the time.
  • giong-http beats the hand-written server on /json, and we do not know why. It is not cheaper: per request it costs 7% more CPU (4.83 against 4.51 µs in the next table), as checking every header and writing Date should. It keeps its core busier (95%), so it gets more out of the same load generator. Treat this row as a measurement of the setup, not as a reason to prefer one over the other.
  • /users separates the batching runtimes from the rest: giong and Monoio at 63–64k, everything else at 35–37k. They send a whole batch of responses in one system call; a server that issues one send per response wakes the other vCPU each time, which is expensive in a virtual machine. On physical hardware expect a smaller gap. giong-http is 9% behind giong here.
  • /compute is the same for everyone, as it should be: the time goes into the function, not the runtime. Differences of a few percent here are code-layout noise.

  • Spinning is the clearest win. With one connection every request finds a sleeping server; keeping it awake cuts median latency from 28 to 19 µs and raises throughput by 48%. It costs CPU: 20.5 instead of 13.6 µs per request, and a spinning worker keeps its core busy between requests.
  • At 5,000 connections giong is the cheapest per request, 11% below hand-written epoll and 16% below tuned Monoio, and has the lowest p99. The likely reason is the provided buffer ring: receive buffers are reused while still warm in cache, where the other servers keep a read buffer per connection. Throughput ranges at 5,000 connections are wide (giong 120–162k, tuned Monoio 103–156k), so the CPU column is the one to read.
  • At 50 and 1,000 connections giong, tuned Monoio and epoll are level on CPU per request (4.4–4.6 µs); raw Tokio is 5–8% more expensive and Glommio 25–60%.
  • p99 is the noisiest number in the table. Raw Tokio's 50 ms at 1,000 connections is the median of five rounds, not a single outlier, but it is still one machine.

Memory per connection

bench/memory.sh: 10,000 connections from one client, four threads per server (giong workers, Tokio worker threads, GOMAXPROCS), median of three rounds, a fresh server for each measurement. The first three columns are the server's resident memory with the connections held, minus before, per connection. "Idle" is a keep-alive connection that has had one request answered, the usual state of a connection from a browser, an app or a pool; "pending" has a request whose handler is waiting (/wait, as for a database or another service). "Under load" is the peak while wrk keeps 5,000 connections busy. giong's two rows were measured again after the packed receive buffers below (0.5), the others are from 0.4's run on the same kind of VM.

ServerOpenIdlePendingUnder load
giong-http1.9 KiB2.0 KiB6.4 KiB15.7 MiB
giong-http on epoll2.1 KiB2.1 KiB6.4 KiB10.4 MiB
Axum (Tokio + hyper)5.7 KiB20.4 KiB19.3 KiB115 MiB
Raw Tokio, own parser12.9 KiB13.1 KiB12.9 KiB64 MiB
Go net/http10.8 KiB18.9 KiB18.3 KiB155 MiB
  • An idle giong connection holds no buffer. What it costs is its task (about 1.2 KB for giong-http's connection), the multishot receive, an idle timer and the socket. The kernel picks a receive buffer only when data arrives; the request and response buffers are taken from a per-worker pool for the length of a request. Hyper keeps an 8 KiB read buffer per connection, Go a 4 KiB reader and writer and a goroutine stack.
  • A handler's future is on the heap only while it runs, in blocks the worker reuses. In giong 0.3 it lived inside the connection's future, and every idle connection was as large as the largest future its handler could make: a handler holding 8 KiB across an .await cost 43 KiB per idle connection. Each wrapper that took a future by value (spawn, timeout, until_shutdown) also kept two copies of it; an idle giong-http connection took 10.9 KiB, one with a pending request 15.0 KiB.
  • "Pending" is mostly the request buffer: 4 KiB, held while the handler runs, because the Request it was given points into it.
  • Receive buffers are a cost per worker, not per connection, and only as many are touched as the traffic needs: a worker lends the kernel 16 at first and twice as many each time a turn of the event loop takes most of them, and reuses the most recently freed first. With 20 workers and 100 busy connections, giong-http's memory rises by 1 MiB (it rose by 40 MiB when every worker lent all 512 buffers at once).
  • Small reads share a buffer. On Linux 6.12 and newer the kernel fills a receive buffer piece by piece (IOU_PBUF_RING_INC), so a hundred connections that each send a short request use one or two buffers rather than a hundred. Before, each receive took a whole buffer, and under load a worker cycled through all it had lent: with 20 workers and 5,000 busy connections giong-http peaked 50 MiB above idle, now 23 MiB (epoll 15 MiB, raw Tokio 64 MiB, Axum 124 MiB, Go 184 MiB; WORKERS=20 SCENARIOS=load, in bench/results/memory-20w/). Requests per second did not change (eight interleaved rounds each at 4 and 20 workers, within this VM's noise).
  • Under load io_uring still holds more than epoll: a response's buffer stays with the kernel until its send completes, and received data stays in its buffer until its connection runs, while epoll writes at once and reads only into a buffer it needs. Older kernels (and GIONG_IO_URING_OFF=packed-buffers) take whole buffers as before.
  • Throughput under load is in the other tables; here the servers and wrk share four vCPUs.

One worker to N

bench/workers.sh measures how throughput grows with the number of workers: the server gets the first N of its CPUs, the connection count grows with N (64 per worker), and the report shows, besides requests per second, the CPU time per request and how busy the server's and the load generator's CPUs were, so a run says which side set the number. It can drive the server from a second machine over ssh (LOAD_HOST, BENCH_HOST), which is how it should be run.

HTTPS

bench/tls.sh: giong-http + giong-tls against Axum + axum-server, both on rustls with ring, so the TLS library and the cryptography are the same and only the runtime, the HTTP layer and the TLS settings differ. The server gets one core and wrk three (the load generator has to encrypt too); 50 connections, TLS 1.3, an ECDSA P-256 certificate, seven interleaved rounds on a 4-vCPU VM (2026-11-17, bench/results/tls/).   • TLS costs giong 2% on /json and 12% on /users, where there are more bytes to encrypt.
  • New connections: 18% more per second than Axum + rustls, at 15% less CPU each, and lower latency (p99 4.2 ms against 7.1). wrk resumes sessions, so these are resumed TLS 1.3 handshakes. Two changes since 0.8.0 (which was 5% behind Axum here): giong-tls sends its session tickets with the first response and its close_notify with the FIN (14.4 TCP segments per connection, both directions, against 16.5 before and Axum's 14.0), and TlsAcceptor::with_certificates picks AES-128-GCM first, as Go's and BoringSSL's servers do, where wrk (OpenSSL) lists AES-256-GCM first and its suite hashes with SHA-384. The suite is most of the gain: Axum set up the same way matches giong's rate (8.4k), with higher latency (p99 6.2 ms against 4.2). A handshake is almost all cryptography, and both use the same library for it.
  • With 64 KiB responses giong-http + giong-tls serves 31.9k req/s against 26.3k for 0.8.0 (+21%), from AES-128-GCM.
  • Axum is lower here than in the first table (94k against 161k) because wrk runs three threads: requests arrive less bunched and Tokio gets less work out of each epoll_wait. giong hardly depends on the shape of the load.
  • One connection per request is not measured for plain HTTP: on loopback that test runs out of client ports (TIME_WAIT) at about 28,000 per second and measures the client.

Kernel TLS pays off for large files, not for data in memory. On bare metal (EPYC 4345P, Linux 7.0, the server on one core), giong-http serving a 1 MiB file with Body::file and kernel TLS reaches 6,104 req/s against 4,484 with rustls in the process (+36%, and 164 µs of CPU per request against 223): sendfile lets the kernel encrypt straight from the page cache. nginx with kernel TLS and sendfile does 6,039 on the same machine. With 64 KiB files, with bodies from memory and with small responses the kernel is 4–22% slower than rustls, so Ktls::Off stays the default. A client receiving 64 KiB bodies gains 11% from letting the kernel decrypt. The whole table and a profile are in the giong-tls README.

The crate's README has the full table, including mysql_async's default pool settings and more connections than the server has cores.

What has not been measured

  • macOS and Windows. Both are correct and tested in CI, but not tuned, and no speed number for them is published yet: the CI runners are shared virtual machines.
  • HTTP/3 end to end, against HTTP/2 on giong and against quinn with h3 on Tokio, on bare metal.
  • More than eight cores, and the other tables on a physical network. The bare-metal run under One worker to N is one pair of 8-core machines; at 16 workers neither side was saturated, so a bigger server and a faster load generator are still needed. The other tables are loopback on one machine.
  • Disks. The file benchmark measures cached data only.
  • Newer Monoio and Glommio. The comparison uses the latest crates.io releases (August and March 2024); their main branches may differ.
