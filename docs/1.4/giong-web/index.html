This is the documentation of giong 1.4 (v1.4.2). The newest release is 1.5: read this page for 1.5.

Routing, middleware and JSON for HTTP services on the giong runtime, on top of giong-http. A handler is a plain async fn; every error, yours or the framework's, is answered as a problem+json body with a stable code (the three answers giong-http gives before a request reaches the app are the exception). No macros, no Tokio.

[dependencies]
giong = "1.4.2"
giong-web = { version = "1.4.2", features = ["serde"] }
serde = { version = "1", features = ["derive"] }
use std::time::Duration;
use giong::net::TcpListener;
use giong_web::middleware::{Compression, Logger, RequestId, Timeout};
use giong_web::{json, Error, Req, Response, Router, Server, Sink};
use serde::{Deserialize, Serialize};

struct State {
    greeting: &'static str,
}

#[derive(Deserialize)]
struct NewUser {
    name: String,
}

#[derive(Serialize)]
struct User {
    id: u64,
    name: String,
}

async fn hello(req: Req<State>) -> Result<Response, Error> {
    let name: String = req.param("name")?;
    Ok(Response::text(format!("{}, {name}!", req.state().greeting)))
}

async fn get_user(req: Req<State>) -> Result<Response, Error> {
    let id: u64 = req.param("id")?; // "abc" is a 400 that names `id`
    if id == 0 {
        return Err(Error::not_found("user_not_found", format!("no user {id}")));
    }
    json(200, &User { id, name: "Ada".into() })
}

async fn create_user(req: Req<State>) -> Result<Response, Error> {
    let new: NewUser = req.json()?; // 415, 400 or 422 with what is wrong
    json(201, &User { id: 1, name: new.name })
}

fn main() -> std::io::Result<()> {
    giong::Builder::new()
        .shutdown_on_signals(true)
        .shutdown_grace(Duration::from_secs(10))
        .build()?
        .run(|_worker| async {
            // Every worker builds its own app: nothing is locked, nothing needs `Send`.
            let app = Router::new()
                .get("/hello/{name}", hello)
                .get("/users/{id}", get_user)
                .post("/users", create_user)
                .layer(RequestId::new())
                .layer(Logger::new(Sink::Stdout))
                .layer(Compression::new())
                .layer(Timeout::new(Duration::from_secs(10)))
                .build(State { greeting: "Hello" });
            let listener = TcpListener::bind("0.0.0.0:8080").expect("bind");
            Server::new().serve(listener, app).await;
        })
}

What it does

  • One way to write a handler. async fn(Req<S>) -> Result<Response, Error>, where S is the state given to build. ? works on any error type: what the client should know is an Error with a status, a code and a detail; anything else becomes a 500 whose cause goes to the log and never to the client.
  • A panic fails one request, not the connection. A handler or middleware that panics is answered with a 500 (GIONG-E1210) whose logged cause is the panic's message, with the request id and the log line of any other error; the connection, and over HTTP/2 every other request on it, carries on. (With panic = "abort" the process still stops.)
  • Typed parameters. req.param::<u64>("id")? and req.query_param::<u32>("page")? parse into any FromStr type. A value that does not parse is a 400 naming the parameter, the value and the type expected. With serde, req.query::<T>() reads the whole query string into a struct and req.json::<T>() the body; their string fields are String, or Cow<'a, str> with #[serde(borrow)], never &str, which cannot hold an escaped value (giong-web answers that 500 with a cause that says so, rather than blame the client). Both query APIs follow one strict rule: a key that is read appears once, and the whole query string is valid percent-encoding, or the answer is a 400.
  • Routing that answers what it can for you. Patterns with parameters (/users/{id}) and a catch-all (/files/{*path}). A literal segment wins over a parameter and a parameter over a catch-all, with backtracking, so /users/me and /users/{id} live side by side. HEAD is answered by the GET route, OPTIONS and 405 with Allow for every path, and a 404 for /users/ asks "did you mean /users?" when that route exists.
  • Errors that explain themselves. Every error answer is an RFC 9457 problem+json body with a code an agent or a client can match on, and the request id when there is one. The codes giong-web uses itself (GIONG-E1201 to GIONG-E1213) each have a page with the cause and the fix in docs/errors.
  • Mistakes in the program fail at startup, not on the first request. Two routes that would answer the same requests, a pattern that is not valid, or middleware settings that cannot work (any origin with credentials) panic with a code and the line that added them.
  • Middleware is one async fn. They run in the order added, and those of a nested router only for its routes and the 404, 405 and preflight answers under its prefix. Included: request ids, JSON-line logs, CORS, gzip and timeouts, and with the tracing feature a tracing span per request.
  • Bodies of any size. The routes of a router with stream_bodies(max) read their request body as it arrives; any handler can write its response body as it is produced. See "Streaming".
  • Tested without a socket. App::handle(request) answers a Request built with Request::from_bytes, so routes and middleware are tested with plain unit tests.
  • Per-worker and lock-free. The app, its state and its middleware live on one worker. A worker that compresses a large body yields to the others' requests every 64 KiB.

Routing

use std::path::PathBuf;
use std::time::Duration;
use giong_web::middleware::Timeout;
use giong_web::{App, Error, Req, Response, Router};

struct State {
    root: PathBuf,
}

fn app(state: State) -> App<State> {
    let members = Router::new()
        .get("/", list_members)          // GET /teams/{team}
        .get("/members/{id}", member)    // GET /teams/{team}/members/{id}
        .layer(Timeout::new(Duration::from_secs(2))); // these routes, and the 404s under /teams/{team}
    Router::new()
        .get("/files/{*path}", file)     // path = "a/b c.txt" for /files/a/b%20c.txt
        .nest("/teams/{team}", members)
        .build(state)
}

async fn list_members(req: Req<State>) -> Result<Response, Error> {
    let team: String = req.param("team")?;
    Ok(Response::text(format!("the members of {team}")))
}

async fn member(req: Req<State>) -> Result<Response, Error> {
    let (team, id): (String, u64) = (req.param("team")?, req.param("id")?);
    Ok(Response::text(format!("member {id} of {team}")))
}

async fn file(req: Req<State>) -> Result<Response, Error> {
    // Never `..`, `.`, NUL or absolute, so it stays under the root.
    let path: String = req.param("path")?;
    let full = req.state().root.join(&path);
    let bytes = giong::fs::read(&full).await?;
    Ok(Response::new(200).body(bytes))
}
  • A path parameter is one segment, percent-decoded; the catch-all takes the rest of the path, at least one character. A pattern has at most 16 parameters.
  • req.param refuses (400, GIONG-E1205) a value that could leave a directory once decoded: a . or .. segment (/files/../x, %2E%2E, ..%2F), a NUL (%00), a / (%2F) in a one-segment parameter, or a catch-all value starting with /. A route that wants such values reads req.param_raw(name), the value as sent, and checks it itself.
  • Which route answers. At each segment a literal beats a parameter and a parameter beats a catch-all. Among the paths that match, the most specific one with a route for the request's method answers: with GET /users/me and DELETE /users/{id}, DELETE /users/me goes to /users/{id} with id = "me". (Routers such as axum's pick the path first and answer 405.) So Allow, in a 405 and in the automatic answer to OPTIONS, lists every method that would route to the URL, from every path that matches. To keep a literal path to its own methods, give it routes for the others.
  • Middleware layered on a nested router run for its routes, and for what giong-web answers by itself for its paths: the automatic OPTIONS (CORS preflights included, through the middleware of the route the preflight asks about) and the 405 for a path of one of its routes, and the 404 for a path under its prefix. So Cors can be layered on the router nested at /api.
  • /users and /users/ are different paths. giong-web does not redirect from one to the other; its 404 names the one that exists.
  • req.route() gives the pattern that matched (/teams/{team}/members/{id}), for logs and metrics.
  • Router::route(method, pattern, handler) takes any method; get, post, put, patch and delete are shortcuts.
  • There is no merge. To keep the routes under one prefix in several routers (public ones and ones behind a key, say), nest each of them at the same prefix: .nest("/api", public).nest("/api", private). Each keeps its own middleware; a 404 under the prefix goes through the first one's.

Errors

400, 422GIONG-E1207a JSON body that is not JSON (400) or does not fit the type (422)
415GIONG-E1208a body that should be JSON and has another Content-Type
503GIONG-E1209Timeout ran out
500GIONG-E1210the handler failed, or a handler or middleware panicked; the cause is logged, never sent
503GIONG-E1211a database or service the handler needs cannot be reached (giong's connect, timeout and pool errors); Retry-After: 1. A statement the database cancelled at its own statement timeout (GIONG-E3004) is not among them: it is a 500
403GIONG-E1212a CORS preflight that Cors refused, saying which of origin, method or header

Your own errors take your own codes: Error::not_found("user_not_found", "no user 42"), Error::conflict(..), Error::new(429, "rate_limited", ..).with_header("Retry-After", "30"). Error::new and with_header panic on a status outside 400..=599 and on a header value with a control character, which suits literals; a status or a value that comes from elsewhere goes through Error::from_status (anything else becomes 502, the status given logged) and try_with_header (Err gives the error back without the header). Error::of(&response) reads the error back from a response, for middleware and tests. Every error response has Cache-Control: no-store.

Not problem+json: what giong-http refuses before the app sees the request. A body larger than the server's max_body_size (413; 1 MiB unless changed, so a large JSON POST is enough), a head larger than its limit (431) and a request that is not valid HTTP (400) are answered by the server below giong-web: the status with an empty body, no code, no X-Request-Id, and no line from Logger or Trace, since no middleware runs. A client should read a 4xx without a body as one of these three. The same goes for a request refused because the worker already holds as many request bytes as the server's max_buffered_request_bytes allows: 503 with Retry-After: 1 and a plain-text body that starts with GIONG-E1120 (over HTTP/2 the stream is refused with REFUSED_STREAM instead); retry it. On a route with stream_bodies, a body announced as longer than the route's limit is refused before the handler runs, the same bare way; one that grows past the limit while the handler reads it is a problem+json 413 (GIONG-E1111).

? finds a giong code anywhere down the error's source() chain, so a pool timeout wrapped in your own error type is still a 503. It reads the code from the type of giong's errors and from the start of the companion crates' messages, never from the text of an io::Error.

Middleware

use giong_web::{Error, Middleware, Next, Req, Response};

struct RequireAuth;
struct UserId(u64);

impl<S: 'static> Middleware<S> for RequireAuth {
    async fn call(&self, mut req: Req<S>, next: Next<'_, S>) -> Result<Response, Error> {
        match req.header_str("authorization") {
            Some(token) if token.starts_with("Bearer ") => {
                req.set_extension(UserId(42)); // the handler reads req.extension::<UserId>()
                Ok(next.run(req).await)
            }
            _ => Err(Error::unauthorized("no_token", "send a bearer token")
                .with_header("WWW-Authenticate", "Bearer")),
        }
    }
}

next.run(req) returns the Response, with an error from further in already turned into its problem+json answer, so a middleware sees and can change every response. The first layer added is the outermost, the reverse of axum's Router::layer (where the last one added is): code ported from axum lists its layers the other way round. Add them in this order, outermost first:

Logger::new(Sink::Stdout)one JSON line per request: time, method, path, route, status, duration, bytes, request id, peer, worker, and for errors the code, detail and causequery strings left out (.include_query(true)); written by a background thread, never on the worker
Cors::new()answers preflights and adds Access-Control-Allow-* for the origins named; on the outermost router or a nested one, before any credentials check (preflights carry none)no origin allowed until named with .allow_origin(..); methods GET, HEAD, POST; no extra headers
Compression::new()gzip for clients that accept itlevel 1, bodies from 1 KiB to 16 MiB; text, JSON, JavaScript, XML (SVG too) and WebAssembly

Trace::new() (feature tracing)runs each request in a tracing span with OpenTelemetry's field names (http.request.method, url.path, http.route, http.response.status_code, client.address) plus request_id and worker, ended by one event; a 5xx at ERROR with its code and causeinstead of Logger, or beside it

A log line:

{"ts":"2026-11-13T09:21:04.118302Z","level":"info","event":"request","method":"GET","path":"/users/42","route":"/users/{id}","status":200,"duration_us":84,"bytes":51,"request_id":"3f9a0c1e7d2b4a59000200000000002a","peer":"10.0.0.7:51122","worker":2}

A request dropped before its response is ready (the client reset its HTTP/2 stream, or a Timeout layered outside the logger gave up) gets a line too, at the drop, with "event":"request cancelled", "status":null and the time until then; Trace ends its span with a request cancelled event.

The log thread batches lines every 10 ms. When it falls behind by more than 1 MiB per worker, lines are dropped and counted in a log_dropped line, instead of the workers waiting or memory growing. Once written, a worker's buffer shrinks back to 64 KiB, and a thread's buffer goes when the thread ends. A path or query string longer than 4 KiB is cut, ending ...(+N bytes). giong_web::flush_logs() waits for what is queued (up to 2 s); dropping an App calls it.

Streaming

use giong_web::{Body, Error, Req, Response, Router};

async fn upload(req: Req) -> Result<Response, Error> {
    // Checked by `param`: no `..` or `.` segment, no NUL, not absolute.
    let name: String = req.param("path")?;
    let body = req.body_stream().expect("a streaming route");
    let mut total = 0;
    while let Some(piece) = body.chunk().await? {
        total += piece.len(); // write it under the uploads directory, hash it, ...
    }
    Ok(Response::text(format!("{name}: {total} bytes")))
}

async fn events(_req: Req) -> Result<Response, Error> {
    let (tx, body) = Body::channel();
    drop(giong::spawn(async move {
        for n in 0.. {
            if tx.send(format!("data: {n}\n\n")).await.is_err() {
                break; // the client went away
            }
            giong::time::sleep(std::time::Duration::from_secs(1)).await;
        }
    }));
    Ok(Response::new(200).header("Content-Type", "text/event-stream").body(body))
}

let uploads = Router::new().put("/files/{*path}", upload).stream_bodies(10 << 30);
let app = Router::new().get("/events", events).nest("/api", uploads).build(());
  • stream_bodies(max) applies to every route of its router, wherever the router is nested. Other routes still get their body in full, within the server's max_body_size.
  • Nothing of the body is read until the handler asks, so a handler can refuse an upload (no credentials, no space) before the client sends it. One piece is in flight at a time: a slow handler slows the client down instead of filling memory.
  • ? on a body error answers 413 (GIONG-E1111, past max) or 400 (GIONG-E1112 cut short, GIONG-E1113 malformed). A body announced past max gets 413 before the handler runs. req.json() on a streaming route is a 500 whose logged cause says to read the stream.
  • Timeout does not limit a streaming route, whose handler runs while the body arrives; each piece still has the server's request_timeout. Work done once the body is in (a database call, an upstream request) needs its own limit: wrap it in giong::time::timeout (the Timeout docs show how). Compression leaves streamed responses alone, and Logger writes "bytes":null for them.
  • A streamed response goes out chunked, each piece as soon as it is sent. send fails once the client has gone (noticed at the next write), so the producer stops.

Testing

use giong_web::{Error, Req, Request, Response, Router};

async fn get_user(req: Req<()>) -> Result<Response, Error> {
    let id: u64 = req.param("id")?;
    Ok(Response::text(format!("user {id}")))
}

let app = Router::new().get("/users/{id}", get_user).build(());
let req = Request::from_bytes(b"GET /users/abc HTTP/1.1\r\nHost: t\r\n\r\n").unwrap();
let resp = giong::block_on(app.handle(req));
assert_eq!(resp.status(), 400);
assert_eq!(giong_web::Error::of(&resp).unwrap().code(), "GIONG-E1205");

Performance

Measured with bench/web.sh: the same handlers on giong-web and on axum 0.8.9 (Tokio 1.54, hyper 1.12), both with serde_json 1.0, each server on one core and wrk on another of a 4-vCPU virtual machine (Xeon 2.1 GHz, Linux 6.18), 50 connections. /json serializes a one-field struct, /users a list of 100 users (8 KB), /users/{id} reads a path parameter, /compute?n=25 a typed query and then computes a Fibonacci number. The middleware rows add request ids, gzip at level 1 from 1 KiB and a 10 s timeout: giong-web's own, and tower-http 0.6.11's for axum; wrk asks for gzip.   • 1.3 times axum on small JSON answers, 1.8 times on the list of users, 1.9 to 2.3 times with middleware. The routes, the parameters and serde cost giong-web about 5% against giong-http's bare handler on /json. giong-http's /users is faster because it writes its JSON by hand, without serde or the 200 small strings the handler builds; giong-web and axum run the same handler.
  • /compute is the handler's time, the same for both within noise (giong-web's range 3.66–4.01k, axum's 3.58–4.07k). Its p99 is higher on giong-web (22.9 against 18.5 ms), as it is on giong-http (24.2 ms). Our guess, not measured: a worker runs every ready request before it reads its sockets again, so when each costs 250 µs of CPU, some wait for a whole batch.
  • Pipelined requests (16 per write): axum stays at 18k, as in the main benchmark; we have not looked into why. giong-http reads a pipeline and answers it as a batch.
  • Resident memory after the run: 6.6 MB for giong-web, 5.2 MB for axum.

HTTPS and a database behind the handlers are measured with the example REST API. Not measured yet: several cores, and middleware one at a time. Results are in bench/results/web/.

Features

FeatureAdds
serdereq.json::<T>(), req.query::<T>() and json(status, &value), through serde and serde_json
tlsServer::serve_tls, through giong-http: HTTP/2 or HTTP/1.1, as ALPN picks
tracingmiddleware::Trace, through tracing 0.1

Apps are served over HTTP/2 as well as HTTP/1.1, with nothing to change: giong-http turns each HTTP/2 stream into the request a handler already knows (see its HTTP/2 section). Over TLS, ALPN picks the protocol; without TLS, a client that knows the server speaks HTTP/2 (prior knowledge) gets it on the same port.

Not there yet

Cookies and sessions, forms and multipart bodies, WebSockets, serving static files, and compressions other than gzip. The crate has had no independent security audit.
