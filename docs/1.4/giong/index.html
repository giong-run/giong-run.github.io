This is the documentation of giong 1.4 (v1.4.2). The newest release is 1.5: read this page for 1.5.

Named after Thánh Gióng, the child of Vietnamese legend who lay silent for three years and then rose a giant: giong costs next to nothing while idle and uses every core the moment load arrives.

Status: 1.4.0. The API has been frozen since 1.0 (STABILITY.md), and every 1.x release only adds. A whole service runs on giong with no Tokio underneath: TCP, UDP, Unix sockets, files, timers, DNS, multi-core and graceful shutdown in the runtime, and twelve companion crates for HTTP/1.1, HTTP/2 and HTTP/3, TLS, gRPC, Protocol Buffers, QUIC, PostgreSQL, MySQL, Redis, routing and middleware, and an MCP server for agents. One service uses it so far, its author's. See Platforms and Limitations.

New in 1.x, each a minor release that needs no code change to upgrade:

ReleaseWhat it added
1.4Windows: a completion-port (IOCP) driver for the runtime crate: tasks, timers, channels, TCP, UDP, files, DNS and Ctrl+C. The other crates come to Windows in later 1.x releases.
1.3HTTP/3: giong-quic (QUIC on giong's UDP sockets) and giong-http's HTTP/3 server and client behind the unstable-http3 feature; UDP offloads (GSO, GRO, ECN) behind unstable-udp-offload.
1.2macOS: a kqueue driver, tested on macOS 15 and 26 on Apple Silicon; a send or connect that meets ENOBUFS waits for buffers (GIONG-E0028).
1.1gRPC: giong-grpc, giong-proto and giong-grpc-build; HTTP trailers and streamed request bodies; Client::preconnect and HTTP/2 pings; batched PostgreSQL reads; uploads of 1 MiB 2.2 times as fast.

The full list is in CHANGELOG.md.

Start here

For people and for AI agents alike, the one path:

  1. Add the crates for the job. A web service: cargo add giong giong-web serde --features serde/derive. A bare HTTP server: cargo add giong giong-http. The table under Choosing crates says which giong crate does each job and what it replaces.
  2. Start one worker per core with giong::Builder::new().shutdown_on_signals(true).build()?.run(|_worker| async { .. }). Each worker binds its own listener on the same port; there is no #[main] macro.
  3. Read the error. Every error giong raises starts with a code (GIONG-E0102: no address found for db.internal. Fix: ...) and links to its page in docs/errors. Match on giong::error::code(&err), never on the text.
  4. Ask the running service when something is slow or stuck: giong-mcp lets your coding agent read each worker, task and pool (below).
  5. Deploy anywhere Linux runs. In Docker it works with no settings; allowing io_uring makes it faster (Run in Docker).

Then read docs/BEST_PRACTICES.md: the shape of a service, state, timeouts, databases, deployment and tests, each rule with its reason. A coding agent gets the same as a skill: skills/giong, or download it from giong.run/docs/agent-skill.

AGENTS.md and giong.run/llms.txt tell a model the facts it gets wrong; the API reference is on docs.rs.

What giong is for

giong is a late entrant: Tokio has been Rust's default runtime for years, and giong does not try to be a smaller copy of it. It is built for the way services are written now, with more and more of the code coming from AI agents. So the API is designed to be used correctly on the first try, and to tell the one who got it wrong how to fix it, rather than to be short to type.

  • The goal: the best async runtime for Rust, on technical merit. A complete, general-purpose runtime for any workload a service has, faster and leaner than Tokio. Every claim comes from a benchmark in this repository, and where giong is not ahead the README says so (see below).
  • A whole service with no Tokio underneath. HTTP/1.1 and HTTP/2 (server and client), TLS, PostgreSQL, MySQL, Redis, DNS, routing and middleware are giong crates, written for its buffer pool and its batched system calls, not adapters. Choosing crates measures each one against the Tokio crate it replaces.
  • Agent-first. Every error giong raises carries a stable code, the cause and the fix, and has a page of its own (docs/errors). AGENTS.md and giong.run/llms.txt tell a model how to work with it; giong-web writes JSON-line logs and tracing spans; giong-mcp lets an agent look inside a running service (below).
  • One major version for a long time. After 1.0, giong grows through 1.x minor releases for years rather than moving to a 2.0, so the API follows four rules:
    1. One way to do each thing.
    2. Misuse fails at compile time, or at run time with a coded error.
    3. Every behaviour code relies on is documented.
    4. Releases only add; they never change what existing code means. The API was settled in 0.7 (review), and cargo-semver-checks runs on every pull request.
  • Linux first, and the same program elsewhere. Tuned and measured on Linux with io_uring, with an epoll driver wherever io_uring is blocked. macOS runs on a kqueue driver, for developing on a Mac; Windows runs the runtime crate on I/O completion ports. One API on all of them: where a system cannot do what Linux does, the difference is a documented cost, never a different result (Platforms).

Let your agent look inside the running service

giong-mcp is an MCP server built into your service. Connect your coding agent (Claude Code, or any client that speaks MCP's Streamable HTTP) and it can see what each worker is doing, which tasks are alive and which line of your code spawned them, what the database pools hold and where the time goes, instead of guessing from logs. The answer no other tool gives: which task blocks a worker, named by the line that spawned it.

  1. Add giong-mcp and start it next to the runtime. It starts only when GIONG_MCP is set, and never stops the service from starting:
    fn main() -> std::io::Result<()> {
    let rt = giong::Builder::new().shutdown_on_signals(true).build()?;
    let _mcp = giong_mcp::start_from_env(&rt.handle()); // keep it: dropping it stops the server
    rt.run(|_worker| async {
        // ... the service ...
        giong::shutdown_signal().await;
    })
}
  2. Run the service with an address and a token (16 characters or more):
    export GIONG_MCP=127.0.0.1:7777 GIONG_MCP_TOKEN=$(openssl rand -hex 16)
cargo run --release
  3. Connect the agent, with the same token:
    claude mcp add --transport http giong http://127.0.0.1:7777/mcp \
    --header "Authorization: Bearer $GIONG_MCP_TOKEN"

The agent then has five tools: overview (memory, threads, open descriptors against the limit, each worker's state, warnings such as a blocked worker), workers (each worker's counters, timers, I/O in flight and the task it is stuck in), tasks (live tasks grouped by the line that spawned them: a count that keeps growing is a leak), sources (the PostgreSQL, MySQL and Redis pools: open, taken, waiting, timeouts) and profile (times every poll for a window and lists where the workers spent it). Every tool only reads, apart from profile turning on poll timing for its window. The server listens on a loopback address or a Unix socket only, needs the token on TCP, and runs on a thread of its own, so it answers even when every worker is stuck. To reach a service on another machine, forward the port (ssh -L, kubectl port-forward).

Why giong

  • One system call per tick, not per operation. Every read, write, accept, close and cancellation a turn of the event loop produces goes to the kernel in a single io_uring_enter, which also returns every completion that is ready. A request costs about 0.03 system calls; an epoll-based server needs 2.
  • A latency dial. Builder::spin_before_park lets a worker watch its ring instead of going to sleep. On a single connection that is 48% more requests and a third less latency (19 µs instead of 28 µs) than without it, and than any other runtime measured here.
  • It holds up when connections pile up. At 5,000 connections giong spends the least CPU per request (11% below the next runtime) and has the lowest p99. At 1,000 it is level with a hand-written epoll server and ahead of the rest.
  • HTTP and HTTPS in the box. giong-http and giong-tls serve HTTPS at 146.6k requests/s on one core, against 81.2k for Axum on the same rustls.
  • Cancellation-safe by construction. Dropping an I/O future never frees memory the kernel may still write to, and wrapping recv, recv_from or accept in a timeout loses neither data nor connections.
  • Runs where io_uring cannot. In a Docker container with the default seccomp profile, under gVisor or on a kernel older than 6.0, a worker switches to an epoll driver by itself: same API, same tests, and as fast as raw Tokio there. See Drivers.
  • gRPC without copies. giong-grpc reads messages as giong-proto views over the receive buffer: a one-thread server does 30% to 50% more 100-byte unary calls than tonic and holds 5.7 kB per open stream against tonic's 11.6 kB.
  • Small enough to read. Three dependencies on any one system (socket2, plus libc and io-uring on Linux, libc on macOS, windows-sys on Windows), and a comment on every unsafe block.

What it is not, today: faster than everything at everything. On the classic 50-connection benchmark giong, a tuned Monoio and raw Tokio are within noise of each other, because the kernel's TCP stack, not the runtime, is most of the cost. Over one PostgreSQL connection shared by every task, giong-postgres is 7–9% behind tokio-postgres; a blocking std read of a cached file beats every async one, giong's included; and a TLS handshake costs the same as Axum's once both prefer the same cipher suite. The benchmark lab, which drives giong, Tokio, Monoio and Glommio with the same program and a neutral load generator, also finds giong behind: Monoio serves 13% more requests on one core; Tokio receives 1 MiB uploads 1.7 times as fast on the bare runtime; and with one request in twenty computing for a millisecond, the short requests' p99 on giong is 1.3 to 1.7 times the best runtime's (Tokio's work stealing, on two cores). macOS and Windows are correct but not tuned, and have no published speed numbers yet. The numbers below say where the design pays off and where it does not.

Quick start

A JSON API on every core, with giong-web:

cargo new hello && cd hello
cargo add giong giong-web serde --features serde/derive
use giong::net::TcpListener;
use giong_web::middleware::{Logger, RequestId};
use giong_web::{json, Error, Req, Response, Router, Server, Sink};
use serde::Serialize;

#[derive(Serialize)]
struct User { id: u64, name: String }

async fn get_user(req: Req<()>) -> Result<Response, Error> {
    let id: u64 = req.param("id")?;   // "abc" is a 400 that names `id`
    if id == 0 {
        return Err(Error::not_found("user_not_found", format!("no user {id}")));
    }
    json(200, &User { id, name: "Ada".into() })
}

fn main() -> std::io::Result<()> {
    giong::Builder::new()
        .shutdown_on_signals(true)                  // Ctrl-C / SIGTERM stop it gracefully
        .build()?
        .run(|_worker| async {
            let app = Router::new()
                .get("/users/{id}", get_user)
                .layer(RequestId::new())
                .layer(Logger::new(Sink::Stdout))   // one JSON line per request
                .build(());
            let listener = TcpListener::bind("0.0.0.0:8080").expect("bind");
            Server::new().serve(listener, app).await;
        })
}
cargo run --release
curl localhost:8080/users/7    # {"id":7,"name":"Ada"}

An HTTP service on every core, with giong-http:

use std::time::Duration;
use giong::net::TcpListener;
use giong_http::{Request, Response, Server};

async fn handler(req: Request) -> Response {
    match (req.method(), req.path()) {
        ("GET", "/health") => Response::text("ok"),
        ("POST", "/echo") => Response::new(200).body(req.body().to_vec()),
        _ => Response::new(404),
    }
}

fn main() -> std::io::Result<()> {
    giong::Builder::new()
        .shutdown_on_signals(true)                  // Ctrl-C / SIGTERM stop it gracefully
        .shutdown_grace(Duration::from_secs(10))    // requests in progress are answered
        .build()?
        .run(|_worker| async {
            // Every worker binds its own listener on the same port (another process
            // cannot take it); the kernel spreads connections across cores.
            let listener = TcpListener::bind("0.0.0.0:8080").expect("bind");
            Server::new().serve(listener, handler).await;
        })
}

For HTTPS, turn on the tls feature and call serve_tls with a giong_tls::TlsAcceptor.

The runtime itself, without the library: a TCP echo server.

use giong::net::TcpListener;

fn main() -> std::io::Result<()> {
    giong::Builder::new()
        .shutdown_on_signals(true)
        .build()?
        .run(|_worker| async {
            let listener = TcpListener::bind("0.0.0.0:8080").expect("bind");
            while let Some(Ok(stream)) = giong::until_shutdown(listener.accept()).await {
                giong::spawn(async move {
                    loop {
                        let Ok(data) = stream.recv().await else { return };
                        if data.is_empty() { return }       // peer closed
                        let reply = data.to_vec();
                        drop(data);                          // buffer back to the pool
                        if stream.write_all(reply).await.0.is_err() { return }
                    }
                });
            }
        })
}

UDP and files: receiving borrows a buffer from the worker's pool, and whatever you hand to the kernel goes in by value and comes back with the result.

use giong::{fs, fs::File, net::UdpSocket};

async fn demo() -> std::io::Result<()> {
    let socket = UdpSocket::bind("127.0.0.1:9000")?;
    let (datagram, peer) = socket.recv_from().await?;      // multishot, cancel safe
    let reply = datagram.to_vec();
    drop(datagram);                                        // buffer back to the pool
    socket.send_to(reply, peer).await.0?;

    let file = File::create("log.txt").await?;
    file.write_all_at(b"hello\n".to_vec(), 0).await.0?;
    file.sync_all().await?;
    let text = fs::read("log.txt").await?;
    assert_eq!(text, b"hello\n");
    fs::rename("log.txt", "log.old").await
}

For a latency-sensitive service on dedicated cores:

fn main() -> std::io::Result<()> {
    let runtime = giong::Builder::new()
        .spin_before_park(std::time::Duration::from_micros(200))
        .build()?;
    runtime.run(|_worker| async { /* ... */ })
}

Run in Docker

giong needs nothing in the image besides the program, and a container needs no special settings: where the default seccomp profile blocks io_uring, every worker runs on epoll by itself and says so once on stderr. A multi-stage build:

FROM rust:1 AS build
WORKDIR /src
COPY . .
RUN cargo build --release --locked

FROM gcr.io/distroless/cc-debian12:nonroot
COPY --from=build /src/target/release/hello /hello
EXPOSE 8080
ENTRYPOINT ["/hello"]

What matters at run time:

  • Stopping. docker stop and Kubernetes send SIGTERM. Build the runtime with .shutdown_on_signals(true) (and .shutdown_grace(..) to answer the requests in flight); a program that runs as process 1 without it ignores SIGTERM until it is killed.
  • Workers follow the CPU limit. giong starts one worker per CPU the container may use: the cpuset, lowered by a CPU quota (--cpus, resources.limits.cpu), rounded down.
  • io_uring for full speed. Docker's and Kubernetes' default profiles block it. docs/DEPLOYMENT.md builds a seccomp profile that is Docker's default plus the three io_uring calls, for docker run, Docker Compose and Kubernetes, and the locked-memory limit (--ulimit memlock=-1:-1) some kernels need. giong::driver_choice() says which driver a worker got and why; log it at startup.
  • Check before you rely on it: GIONG_DRIVER=io_uring makes the runtime refuse to start where io_uring is blocked (GIONG-E0001) instead of falling back.

Five things to remember:

  1. recv() returns a RecvBuf borrowed from the worker's pool. An empty buffer means the peer closed the connection. Copy what you need and drop it; do not hold it across an .await.
  2. recv(), recv_from() and accept() are cancel safe: a timeout around them loses no data, datagram or connection. The one-off operations (read, read_from, read_at on a pipe) are not: one that is dropped mid-flight can still take data that arrives before the kernel has processed the cancellation.
  3. A datagram received with recv_from() lives in a pool buffer, so its longest payload is the buffer size minus 44 bytes (16 KiB − 44 by default). Longer ones are cut off and is_truncated() says so; raise .recv_buffers(count, size) or use read_from() with a buffer of your own. Do not mix the two kinds on one socket.
  4. A File has no cursor: every read and write names its offset. Opened with append(true), writes go to the end whatever the offset.
  5. Timers fire at their deadline, to the precision of the kernel's wake-up (a 1 ms sleep takes about 1.05 ms on Linux), and never early.

Choosing crates

For each job a service has, try these in order and take the first that fits:

  1. A giong crate. Each one was written for giong: it reads into the worker's buffer pool, hands owned buffers to the kernel, and batches system calls (many requests per read and many answers per write on a connection, and the statements of every task pipelined over a pool's few connections). Most were measured against the Tokio crate they replace, with the factors in the table below.
  2. A crate that needs no runtime. serde, rustls, futures' combinators, Tokio's sync module (Semaphore, Notify, watch, broadcast), and anything else built only on std::future, run on giong as they are.
  3. A Tokio-ecosystem crate that takes a stream from you, over giong_compat::Compat: h2, tokio-rustls, tokio-tungstenite, hyper's conn API, tokio-util's codecs. This is the bridge for a protocol giong has no crate for yet (WebSocket, for one), not a second way to do what a giong crate does.
  4. A crate that needs the Tokio runtime (reqwest, sqlx, tonic's transport, redis-rs, most cloud SDKs) does not run on giong's workers: it panics with "there is no reactor running", or never finishes. Where a giong crate is not ahead, the sections linked above say so: over one shared connection giong-postgres is 7–9% below tokio-postgres at the median, a blocking std read of a whole small cached file beats every async one, Monoio and Glommio spawn tasks and pass values within one thread faster, and TLS handshakes cost the same on both once axum's rustls is set to the cipher suite giong-tls prefers.

What Compat adds is measured on its own, on one TCP stream with no protocol on top (giong-compat): large writes go straight from the caller's memory to the socket, from 9% above to 6% below Tokio's CPU per byte sent over the last two sessions (until 0.8.0 they were copied first: 25% above Tokio in a session the same day); against giong's own recv, 6–16% more CPU per byte read with read, and no measurable difference through AsyncBufRead; up to 5% more CPU per small request and reply, and level with Tokio there. Receiving costs more CPU per byte than Tokio's own (14% through AsyncBufRead, 19% with read, in the latest session, with 16 KiB receive buffers; 17% and 30% with 8 KiB), most of it in giong's own receive (12% above Tokio). A protocol crate over Compat brings its own design on top of that, and none has been measured against the giong crate for the same protocol. The reason to prefer the giong crate is its design (step 1) and the gaps in the table, measured against these Tokio crates on Tokio: running one of them on giong through Compat does not change how it reads, writes or pipelines, and adds the copies above.

To tell steps 3 and 4 apart: a crate of step 3 takes a stream you made (S: AsyncRead + AsyncWrite) and gives back a future or a connection object for your task to poll. A crate of step 4 opens its own sockets (connect(url)), sleeps or spawns: cargo tree -e features -i tokio shows it turning on Tokio's net, time, rt or process feature. Running it once settles it.

Design

        worker 0                 worker 1                 worker N
 ┌────────────────────┐   ┌────────────────────┐   ┌────────────────────┐
 │ tasks (!Send)      │   │                    │   │                    │
 │ run queue          │   │        ...         │   │        ...         │
 │ timer wheel        │   │                    │   │                    │
 │ receive buffers    │   │                    │   │                    │
 │ its own io_uring   │   │                    │   │                    │
 └─────────┬──────────┘   └─────────┬──────────┘   └─────────┬──────────┘
           │   eventfd + injector (only when another thread wakes a task)  │
           └──────────────────────────┴────────────────────────────────────┘

Each worker is a thread pinned to one core that owns everything it touches. Its loop:

run the tasks that are ready  →  io_uring_enter (submit everything, collect everything)  →  fire timers  →  repeat
PartHowWhy
ThreadsThread-per-core, shared-nothing. A task never changes thread.Futures need not be Send; Rc and RefCell just work. No locks on the hot path.
WakersA waker does not own its task; it holds a slot number and a handle to the worker. Same thread: push onto the local queue. Other thread: injector plus eventfd.Wakers must be Send + Sync although tasks are not. This gets there without unsafe.
I/OEverything a tick produces enters the kernel in one io_uring_enter, with DEFER_TASKRUN and SINGLE_ISSUER, through the thread's registered ring descriptor (5.18+).The fewest system calls possible; completions are processed only when the worker asks.
Accept and receiveMultishot accept; multishot receive with a provided buffer ring, for TCP, Unix sockets and UDP (recvmsg). On Linux 6.12+ streams fill each buffer piece by piece (IOU_PBUF_RING_INC).One submission for the life of a listener, connection or socket. The kernel picks a buffer only when data arrives, so the buffer is warm in cache and idle connections hold none; connections that send a little share a buffer.
Writes and filesOwnership passing: write_all(buf) returns (result, buf). TCP sends of 16 KiB and more from bytes that cannot change (&'static, Rc<[u8]>, Arc<[u8]>) go out without a copy on 6.2+ (SEND_ZC), and the write still returns as soon as they are queued. File operations are ordinary entries in the same ring.The kernel keeps a pointer to the buffer until it is done; this API makes that sound in Rust. Files need no pool of blocking threads.
CancellationWhen a future is dropped mid-flight, its buffer moves to the driver, a cancel is sent, and the memory is freed only when the kernel confirms.Avoids use-after-free, the classic bug of completion-based runtimes.
BackpressureA reader more than an eighth of the pool behind has its multishot receive paused (TCP then slows the sender), and its backlog copied off the pool while the pool runs low. A dry pool reclaims buffers that hold data left unread for a whole turn of the event loop. An accept backlog over 1,024 pauses the accept.One stalled connection cannot starve the rest, and a busy one that keeps up is never copied.
TimersA hierarchical timing wheel in user space (six levels of 64 slots, 1 ms ticks), with each timer's exact deadline: the worker sleeps until the earliest one.Arming and cancelling are O(1) and make no system call. Nearly every timer is an I/O timeout that is cancelled before it fires.
Latency dialOptionally busy-poll the ring for a while before sleeping.A sleeping thread must be woken by an interrupt and rescheduled, which costs tens of microseconds, more in a virtual machine.
PanicsA panic in a task is caught and reported through its JoinHandle.One bad connection does not take down the worker.
ShutdownWith a grace period, a worker keeps running its tasks after its main future returns, until they finish or the period ends. Then: cancel everything, wait for the kernel to confirm, free. If confirmation does not come, leak on purpose.Requests in progress are answered. Memory safety matters more than a few megabytes at exit.
Old kernelsThree ring setups, tried in order: DEFER_TASKRUN (6.1+), COOP_TASKRUN (6.0), no flags.The same code runs on 6.0; the two fallbacks are tested on every change by forcing them.
No io_uringAn epoll driver behind the same operations, chosen when the ring cannot be set up.Containers and sandboxes that block io_uring still run giong (see Drivers).

Drivers

Each worker runs on one I/O driver, behind the same API. Linux has two:

  • io_uring, the default, which everything above describes. It needs Linux 6.0 or newer and the three io_uring system calls.
  • epoll, chosen without being told where io_uring cannot be set up: a Docker container with the default seccomp profile, Kubernetes with RuntimeDefault, gVisor, the kernel.io_uring_disabled sysctl, or a kernel older than 6.0 (tested on 5.15). docs/DEPLOYMENT.md shows how to allow io_uring where it is blocked.

Builder::driver(DriverKind::IoUring), or GIONG_DRIVER=io_uring, makes the runtime fail to start where io_uring is missing (GIONG-E0001) instead of falling back; DriverKind::Epoll, or GIONG_DRIVER=epoll, chooses epoll anywhere. A fallback is said once on stderr, with the reason, and giong::driver_choice() tells which driver a worker got, who chose it and why. Kernel bugs that would cost io_uring are worked around: Ubuntu 24.04's 6.8 kernels from 6.8.0-135 on refuse correctly formed buffer rings, and giong registers its ring the way they accept (DEPLOYMENT.md). The whole test suite runs on both drivers, and in CI also inside a Docker container with the default profile, on a real 5.15 kernel and on Ubuntu 24.04's own kernel; CI fails if giong would not choose io_uring where it should.

On epoll giong is an epoll runtime like the others and as fast as they are (two system calls per request, the same requests per second as raw Tokio); what sets it apart comes from io_uring, such as 70% more requests per second on 8 KB responses. The measured table is under io_uring against epoll.

The other systems have one driver each, chosen by default (DriverKind is non_exhaustive; asking for a driver the system does not have fails with GIONG-E0004):

  • kqueue on macOS (DriverKind::Kqueue): the readiness loop of the epoll driver, files on the pool of blocking threads, a wake-up through EVFILT_USER. The workers of an address share one socket bound without SO_REUSEPORT, so no other process can take the port.
  • I/O completion ports on Windows (DriverKind::Iocp, GIONG_DRIVER=iocp): operations complete the way they do on io_uring, so buffers are handed over and handed back the same way. Multishot accept is AcceptEx into a socket made ahead; an idle connection waits with a zero-byte receive and holds no buffer; a dropped operation is cancelled with CancelIoEx and its buffer kept until the kernel lets go of it. Windows has no SO_REUSEPORT, so the workers of an address share one socket: connections are handed to them in turn, datagrams by a hash of the sender's address.

Not verified, and you should know it:

  • Neither sanitizer nor valgrind can see the kernel writing into memory, so cancellation safety rests on the design and on tests/cancel.rs.
  • valgrind 3.22 cannot run the multi-threaded tests (it treats io_uring_enter as non-blocking, so threads starve each other); ThreadSanitizer covers those.
  • Every crate, the unsafe code and the workspace's security were reviewed before 0.6, and what was found is fixed there (see the changelog), but the reviewers were the project's AI agents, each reading code it had not written. No outside person has audited giong.
  • giong-tls has had a security review of its own code and of every crate that uses it, which found and fixed two medium issues, but it was done by the project's AI agent, not by an independent auditor. The cryptography and the protocol are rustls's; giong's part is connecting rustls to the socket.

Monoio is the mature choice and runs in production at ByteDance; if you need Tokio-compatible crates today, use it. Glommio is built for storage engines: Direct I/O and priority scheduling are its strengths, not HTTP. giong's case: the receive path (multishot with provided buffers, cancel safe without a second API), good defaults, the latency dial, its own crates for a whole service instead of a compatibility layer, an API held to the four rules above, and code small enough to audit. It is younger than both, and one service runs on it so far.

Limitations

  • Windows has the runtime crate only. In 1.4 giong builds and runs there (tasks, timers, channels, TCP, UDP, files, DNS from the network adapters, Ctrl+C); Unix sockets do not exist there, and giong-http, giong-tls, the database clients, giong-grpc, giong-quic and giong-mcp are not built or tested on Windows yet. Trust roots from the Windows certificate store and processor groups beyond 64 CPUs are missing too.
  • macOS is for development. Correct and tested on every change, not tuned: files run on a pool of blocking threads, CPU pinning is skipped, kernel TLS and UDP segmentation offloads are Linux only, and the listen backlog is macOS's 128.
  • HTTP/3 and the UDP offloads may still change. They are behind the unstable-http3 and unstable-udp-offload features, outside the 1.x stability promise until they are stabilised, and giong-quic runs on quinn-proto's engine for now.
  • Name resolution reads files and DNS only. connect and lookup_host resolve names without blocking, from /etc/hosts and the DNS servers in /etc/resolv.conf; other Name Service Switch sources (mDNS, LDAP) are not used. bind takes IP addresses only, so it never waits on a lookup. fs::read_dir reads each batch of entries with a direct system call on the worker (io_uring cannot read directories): quick on a local disk, a network round trip on NFS. On the epoll driver, file operations run on a pool of blocking threads, and one that is cancelled while running finishes there. Also missing: Unix datagram sockets, multicast, set_len, file locks, O_DIRECT with registered buffers.
  • giong-tls has had no independent audit (see the self-review).
  • The Tokio ecosystem only through I/O traits. Crates that are generic over the stream and driven by you (h2, tokio-rustls, tokio-tungstenite, hyper's connection API, tokio-util's codecs) run on giong through giong-compat, at the cost of a copy. Crates that need the Tokio runtime itself (its reactor, timers or tokio::spawn, as in sqlx, reqwest or tonic's transport) do not. Crates that only use std::future do. For PostgreSQL, use giong-postgres; for MySQL, giong-mysql; for Redis, giong-redis; for HTTP requests, giong-http's client.
  • Started tasks do not migrate. Balancing happens where work starts: jobs queued with Handle::spawn_balanced go to the first idle worker, and listeners bound with TcpListener::bind_balanced hand new connections to less busy workers. A connection already being served stays on its worker, however busy that worker gets.
  • Graceful draining is opt-in. By default, when a worker's main future returns, the remaining connections are dropped. Set .shutdown_grace(..) and use until_shutdown in the connection loop (giong-http does). Connections still in the kernel's accept queue when the listener closes are refused; have the load balancer stop sending first.
  • Unused so far: fixed files, which would save 0.6% of a request, and SQPOLL, which cost more CPU than it saved on bare metal. Zero-copy send covers only bytes that cannot change (&'static, Rc<[u8]>, Arc<[u8]>); a Vec is copied.
