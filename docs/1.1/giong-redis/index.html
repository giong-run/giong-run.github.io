giong-redis

A Redis client and pool on RESP3. The commands of every task pipeline over one connection.

This is the documentation of giong 1.1 (v1.1.0). The newest release is 1.5: read this page for 1.5.

A Redis client and connection pool for the giong runtime. It speaks RESP3 itself, encrypts with giong-tls, and depends on nothing from the Tokio ecosystem.

[dependencies]
giong = "1.1.0"
giong-redis = "1.1.0"
use std::time::Duration;
use giong_redis::{cmd, Client, Config};

fn main() -> Result<(), giong_redis::Error> {
    let config = Config::from_url("redis://localhost:6379")?;
    giong::block_on(async {
        let client = Client::connect(&config).await?;
        client.set_ex("session:42", "data", Duration::from_secs(3600)).await?;
        let session: Option<String> = client.get("session:42").await?;
        // Any command, read as the type asked for.
        let top: Vec<(String, f64)> = client
            .query(&cmd("ZRANGE").arg("leaders").arg(0).arg(9).arg("REV").arg("WITHSCORES"))
            .await?;
        println!("{session:?} {top:?}");
        Ok(())
    })
}

In a service, make one Pool per worker. Nothing is shared between threads, so nothing is locked:

use giong_redis::{Config, Pool};

fn main() -> std::io::Result<()> {
    let config = Config::from_url("redis://cache.internal:6379")?;
    giong::Builder::new().build()?.run(move |_worker| {
        let pool = Pool::new(config.clone(), 2);
        async move {
            // ... serve requests, each one calling pool.get(..), pool.incr(..) ...
            let hits = pool.incr("hits", 1).await.unwrap();
            println!("{hits} hits");
        }
    })
}

What it does

  • Pipelining across tasks. Tasks that share a connection send their commands together, and one round trip answers all of them, with no lock and no task in between. One connection serves hundreds of concurrent tasks.
  • Any command, read as the Rust type asked for. cmd("ZADD").arg(key).arg(score).arg(member) builds a command; the reply converts to Option<String>, i64, bool, Vec<u8>, Vec<T>, HashMap, BTreeSet, tuples or Value. Methods for the everyday commands (get, set, set_ex, incr, hgetall...).
  • Pipelines and transactions. Pipeline sends several commands at once; .atomic() wraps them in MULTI/EXEC. watch gives optimistic transactions with WATCH.
  • Commands that would break sharing are refused before they are sent, with what to use instead. On a shared connection, SELECT would move every task to another database, MULTI would pull their commands into a transaction, and BLPOP would hold them all up for seconds; other clients let that happen.
  • Pub/Sub on a connection of its own, with patterns. Waiting for a message can be cancelled (a timeout, a select) without losing one.
  • A pool per worker. Commands share the least busy connection and steer away from one stuck behind a slow command; take() gives a task a connection to itself, for WATCH and blocking commands, in turn even when shared commands keep the pool busy. Connections that close, or whose server became a replica after a failover (READONLY), are replaced.
  • Limits everywhere, all finite by default: connecting, every reply, the size of a reply, waiting for the pool. A reply that times out or is too large fails alone: the connection stays usable for the other tasks.
  • Errors that say what to do, with the server's error code (WRONGTYPE, NOSCRIPT...) to match on.
  • ACL users, TLS (always verified), Unix sockets, and connection URLs.

RESP3 needs Redis 6 or later; Valkey works too.

Connecting

use std::time::Duration;
use giong_redis::{Config, Error};

fn configs() -> Result<(), Error> {
    let config = Config::from_url("rediss://app:secret@cache.internal:6380/2")?;

    let same_place = Config::new()
        .host("cache.internal")
        .port(6380)
        .user("app")
        .password("secret")
        .database(2)
        .response_timeout(Duration::from_millis(500));
    let _ = (config, same_place);
    Ok(())
}

A URL is redis://user:password@host:port/database?param=value, rediss:// for TLS, and redis+unix:///run/redis/redis.sock?db=2 (or unix://) for a Unix socket; in code, a host starting with / is a socket. redis://:secret@host gives a password alone, for requirepass. The parameters understood are db, client-name, connect-timeout and response-timeout (seconds, as 0.5), and cacert (a PEM file of the authorities to trust, for rediss://). Any other parameter is an error, not silently ignored.

A connection logs in, names itself and selects its database once, when it opens (HELLO 3 AUTH ... SETNAME ..., then SELECT), in one round trip.

TLS is used for rediss:// and when Config::tls asks for it: the server's certificate is checked against the certificate authorities installed on the machine, or the ones given (Tls::Verify(TlsConnector::with_root_pem(..)?)), and against the host name. There is no setting that skips the check. redis:// and Unix sockets do not use TLS.

Sharing a connection

Every method of Client that sends a command takes &self, so tasks share one by cloning an Rc or by holding a reference, and their commands are pipelined. A few commands change the connection itself, for every task on it, and are refused (ErrorKind::Command, before anything is sent):

CommandUse instead
MULTI, EXEC, DISCARDPipeline::new().add(..).atomic()
WATCH, UNWATCHclient.watch(&keys), on a connection the task has to itself (pool.take())
SELECTConfig::database
AUTH, HELLOConfig::user and Config::password
SUBSCRIBE, PSUBSCRIBE, SSUBSCRIBE and their oppositesPubSub::connect
BLPOP, BRPOP, BLMOVE, BZPOPMIN, XREAD ... BLOCK, WAIT...client.query_blocking(..), which takes &mut self
MONITOR, SYNC, PSYNC, REPLCONF, QUIT, RESET, CLIENT REPLYNothing: they make no sense on a shared connection.

A blocking command inside an atomic pipeline does not block (Redis runs it with a timeout of zero), so it is allowed there.

use giong_redis::{cmd, Error, Pipeline, Pool};

async fn demo(pool: &Pool) -> Result<(), Error> {
    // One round trip, run as one transaction.
    let (count, _): (i64, bool) = pool
        .pipeline(
            &Pipeline::new()
                .add(cmd("INCR").arg("visits"))
                .add(cmd("EXPIRE").arg("visits").arg(60))
                .atomic(),
        )
        .await?;

    // A job queue: a connection to itself, waiting up to 10 seconds.
    let mut conn = pool.take().await?;
    let job: Option<(String, String)> = conn
        .query_blocking(&cmd("BRPOP").arg("jobs").arg(10))
        .await?;
    println!("{count} visits, job {job:?}");
    Ok(())
}

API

Client::connect(&config)Opens a connection: TCP or Unix socket, TLS, HELLO, SELECT, all within connect_timeout.
client.query::<T>(&cmd(..).arg(..))Any command, its reply converted to T.
client.get, set, set_ex, set_nx, del, exists, expire, incr, mget, hget, hset, hgetall, publish, pingThe everyday commands, with typed arguments and replies.
client.pipeline::<T>(&pipeline)Several commands in one write; T reads the array of their replies (a tuple, a Vec...). A command that failed fails the conversion with its error; read the replies as Vec<Value> to see each one. With .atomic(), a transaction.
client.watch(&keys)WATCH, then watch.query(..) to read and watch.exec(&pipeline) to run a transaction, which returns None when a watched key changed. Dropping the Watch, or the watch call before it returns, sends UNWATCH.
client.query_blocking(..)A blocking command, without the response timeout (its own timeout argument bounds it).
client.server_version(), server_name(), connection_id()What the server said when connecting; the id is the one CLIENT KILL ID takes.
client.is_closed(), client.in_flight()Whether the connection is closed; how many commands are waiting for their reply.
PubSub::connect(&config)A connection for subscriptions. subscribe, psubscribe, unsubscribe, punsubscribe, each returning once the server confirmed it; next_message() returns a Message with channel(), pattern() and payload().
Pool::new(config, max_size)A pool for the current worker. Connections are opened when needed, up to max_size.
.wait_timeout(duration)How long take() and the command methods wait when every connection is taken, 5 s by default.
.idle_timeout(duration), .max_lifetime(duration)Close a connection unused for this long (10 min by default); replace one older than this (30 min, less up to 10% so that connections opened together are not replaced together).
pool.query(..), pool.pipeline(..) and the command methodsRun on the least busy connection, pipelined with other tasks' commands.
pool.take()A PooledClient for this task alone, which derefs to Client. For WATCH and blocking commands. When the pool is full, tasks waiting here are served in order: a connection is set aside for the first, shared commands go to the others (they keep at least one unless max_size is 1), and it is handed over once the commands already on it are answered. A connection whose blocking command was cancelled while still running is closed instead of coming back.
pool.stats()Connections open, taken, being opened; commands in flight; tasks waiting; and counters for connections opened, connect errors, wait timeouts and connections recycled.

A Client belongs to the worker that opened it (it is not Send, like everything in giong).

Types

Arguments are anything that implements ToArg: strings, byte slices and vectors, integers, floats, and references to them. Implement it for your own types, such as typed keys: whatever write_arg writes, in as many pieces as it likes, is sent as one argument.

use giong_redis::{ArgWriter, ToArg};

struct SessionKey(u64);

impl ToArg for SessionKey {
    fn write_arg(&self, out: &mut ArgWriter<'_>) {
        out.write(b"session:");
        self.0.write_arg(out); // "session:42", one argument
    }
}

Replies convert with FromValue:

RustReads
Option<T>Nil as None, anything else as T. A missing key read into a type that is not an Option is an error that says so.
String, Vec<u8>Bulk, simple and verbatim strings; String only if they are UTF-8, Vec<u8> always.
i8 ... i128, u8 ... u64Integers, and strings that hold one, when the value fits.
f64, f32Doubles (RESP3), integers, and strings that hold a number (ZSCORE's reply).
boolBooleans, and the integers 0 and 1 (EXISTS, SISMEMBER).
()Any reply but an error, discarded (OK).
Vec<T>, HashSet<T>, BTreeSet<T>Arrays and sets; a map as (key, value) pairs.
HashMap<K, V>, BTreeMap<K, V>Maps (HGETALL, CONFIG GET), and flat arrays of keys and values (a stream entry's fields).
Tuples of 1 to 6An array of exactly that many replies ((String, f64) for WITHSCORES pairs).
ValueAny reply, as it arrived. #[non_exhaustive]: a match on it needs a _ arm, so that a later RESP type is not a breaking change.

A conversion never loses anything silently: a number that does not fit, bytes that are not UTF-8, or an array of the wrong length fails with ErrorKind::Type and names what arrived and what to read it as. Implement FromValue for your own types.

Errors

Error is cheap to clone, implements std::error::Error, and converts into io::Error. error.kind() says what went wrong. Each kind has a giong error code, shown in front of the message and linked to its page in docs/errors (GIONG-E3204: WRONGTYPE Operation against a key holding the wrong kind of value. See …); after ? into an io::Error, giong::error::code(&err) finds it:

ErrorKindCodeMeaning
ConfigE3201The configuration or URL is not valid.
ConnectE3202Name resolution, TCP, TLS, the handshake, or the connect timeout. Also a server older than Redis 6 and a database number the server does not have.
AuthE3203The server refused the user name or the password.
ServerE3204The server answered with an error; error.server_code() is its code (ERR, WRONGTYPE, NOSCRIPT, READONLY...).
TypeE3205A reply could not be converted to the Rust type asked for.
CommandE3206The command would break sharing the connection, and was not sent; the message says what to use instead.
TooLargeE3207The reply was larger than max_reply_size. The connection stays usable.
ClosedE3208The connection is closed. A Pool replaces it by itself.
PoolTimeoutE3209No pooled connection became free within wait_timeout.
ProtocolE3210The server sent something that is not RESP3. The connection is closed.
TimeoutE3211No reply within response_timeout. The command may still have run; the connection stays usable.

error.is_transient() is true for errors worth retrying after a pause: connecting, a closed connection, timeouts, and the server's LOADING, BUSY, TRYAGAIN, MASTERDOWN and CLUSTERDOWN. An error from the server affects only its own command: the commands that other tasks pipelined on the same connection get their own replies.

Limits

SettingDefaultWhat happens at the limit
Config::connect_timeout10 sErrorKind::Connect, "connect timeout".
Config::response_timeout30 sErrorKind::Timeout for that command; its reply is thrown away when it comes, and the connection goes on. Set it near what the caller can wait, such as 500 ms for a cache.
Config::max_reply_size64 MiBErrorKind::TooLarge; the reply is read and thrown away as it arrives, without being held in memory. A reply counts for its bytes plus 48 for each element, the Value it becomes, so the limit bounds the memory a reply takes: a million 10-byte members are 17 MB as sent and count for 65 MB.
Pool::wait_timeout5 sErrorKind::PoolTimeout.
Pool::idle_timeout10 minThe connection is closed.
Pool::max_lifetime30 min, less up to 10%The connection takes no new command and is closed once the ones on it are answered (one taken with take(), when it comes back); a new one is opened when needed.

Replies nested more than 128 deep, and lines over 1 MiB (an error message, a number), are refused as protocol errors.

Performance

Measured with bench/redis.sh against redis-rs 1.8.1 (a MultiplexedConnection) and fred 10.1.0 (a Client, with its automatic pipelining), both on Tokio 1.54 with a current-thread runtime. All three pipeline the commands of tasks that share a connection. Each client runs on one core; Redis 7.0.15 (no persistence, io-threads 3) runs on the other three cores of a 4-vCPU virtual machine (Xeon 2.1 GHz, Linux 6.18), reached over TCP on 127.0.0.1. 64 tasks send commands back to back: GET and SET of a 64-byte value, GET of an 8 KiB value, and MGET of ten 64-byte values. Medians of 5 rounds of 5 s, commands per second; µs/op is the client core's time per command (user and system).

One connection shared by the 64 tasks:

  • Small commands: 1.1 to 1.8 times redis-rs, at half its CPU time per command or less. With one connection none of the clients is held back by its core (giong-redis uses about half of it): the round trip is the limit, and giong-redis's is shorter, so its tasks send more. With four connections, redis-rs and fred use all of their core (97–98%), and giong-redis does 1.6 to 1.8 times redis-rs.
  • Large values are mostly the kernel's work. For 8 KiB values about half of the client's core is time in the kernel, receiving the data, whatever the client. giong-redis has the kernel write replies straight into the connection's read buffer (up to 64 KiB per receive), so each byte is copied once on its way in, where reading through the runtime's pooled buffers copied it twice; that took four connections from level with redis-rs (259k against 269k) to 1.25 times it (345k against 276k), and one connection to 2.5 times it.
  • How many connections. The server above has I/O threads; most run without them, as Redis does by default. Against Redis without I/O threads (bench/results/redis/no-io-threads.txt), giong-redis reads 645k GETs per second with one connection, 925k with two, and 845k with four; the server's single thread is then the limit. So a Pool of one or two connections per worker is enough for one Redis server, and more only add to its work. redis-rs does best with two too, 542k.

Cutting the client's own cost per command took the profile further than the first version: the command methods write their command straight into the connection's buffer, with no allocation; a reply is not kept in a Vec of its own; the read buffer moves what is left of a reply only when it is short of room, instead of on every read; and each connection has one timer, set for the oldest command waiting, instead of one per command (a test checks that every command still times out on its own deadline, and never early). Together they took GET with four connections from 660k to 881k per second.

Not measured: a server on another machine (network latency, where pipelining matters more), Redis 7.2 and later, Valkey, TLS, more than one client core, fred with its own pool type. Results are in bench/results/redis/.

Not there yet

Redis Cluster (a MOVED or ASK reply is an error that says so) and Sentinel, client-side caching (CLIENT TRACKING can be turned on with query, but a Client passes over the invalidations it brings), sharded Pub/Sub (SSUBSCRIBE), RESP2-only servers (Redis 5 and older), and streaming a large reply in pieces (a reply is collected in full, up to max_reply_size). Proxies that do not pass HELLO 3 on (twemproxy, Envoy's Redis proxy) cannot be used, since the client speaks RESP3 only. An independent review before 1.0 found problems that have since been fixed (see the changelog); the crate has had no outside security audit.

The tests find redis-server through GIONG_REDIS_BIN (the directory that holds it), /usr/bin or PATH. They skip when Redis is not installed, unless GIONG_REDIS_REQUIRED=1 (CI sets it, and installs Ubuntu's Redis 7.0). They also pass under ThreadSanitizer and on the fallback io_uring setups (scripts/check.sh tsan and fallback). CI runs them against Redis 7.0 (Ubuntu's package) on every pull request, and against Redis 6.2, Redis 7.4 and Valkey 8.0 in its servers job.
