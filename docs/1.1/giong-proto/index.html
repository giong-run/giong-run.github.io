This is the documentation of giong 1.1 (v1.1.0). The newest release is 1.5: read this page for 1.5.

Protocol Buffers for giong: messages decoded as views over the receive buffer. Strings, bytes, repeated fields and maps borrow from the input, so decoding copies nothing and makes no heap allocation; encoding writes message structs whose fields borrow too. Code is generated from .proto files by giong-grpc-build, which parses them in Rust: no protoc to install.

New in giong 1.1. It is the message layer of giong-grpc, gRPC on giong's HTTP/2.

Use

build.rs:

fn main() {
    giong_grpc_build::compile(&["proto/shop.proto"], &["proto"]).unwrap();
}

The crate:

mod pb {
    include!(concat!(env!("OUT_DIR"), "/giong_proto.rs"));
}
use giong_proto::Encode;
use pb::shop::v1::{LineItem, Order, OrderView};

// Encode: a message struct whose fields borrow. `..Default::default()` keeps the
// code compiling when fields are added to the .proto.
let items = [LineItem { sku: "TEA-001", quantity: 2, ..Default::default() }];
let bytes = Order { id: 1001, customer: "Nguyễn Văn A", items: &items, ..Default::default() }
    .encode_to_vec()?;

// Decode: checks the whole message once, then every accessor is infallible and
// returns data borrowed from `bytes`.
let order = OrderView::decode(&bytes)?;
assert_eq!(order.customer(), "Nguyễn Văn A");
for item in order.items() {
    println!("{} x{}", item.sku(), item.quantity());
}

examples/proto-hello is a complete program with enums, oneofs, maps, optional fields and a service (cargo run -p proto-hello).

What is generated

For each message M in package a.b (module a::b):

ItemWhat it is
MView<'a>the decoded message. MView::decode(&buf) checks everything protobuf requires, then accessors return &'a str, &'a [u8], numbers, Enum<E>, nested views, and &Repeated / &Map for repeated fields and maps, read lazily from the buffer. Singular fields with presence (proto2, proto3 optional) have has_x(); absent fields return their default (proto2 [default = ...] included).
M<'a>the message to build and encode: plain public fields (&'a str, &'a [T], Option<&'a Sub>, &'a [(K, V)] for maps). Implements Encode.
m::OneofView<'a>, m::Oneof<'a>an enum per oneof, for each side. Nested messages and enums are in the module m.
Ea Rust enum per protobuf enum; fields hold Enum<E>, which keeps numbers the enum does not define (.known(), .raw()).
service::METHODfor each service, a module with the :path and kind (unary, client, server or bidi streaming) of every method, for giong-grpc.

A view's Encode writes the bytes it was decoded from, unchanged (a view cannot be modified, so they are its encoding): forwarding a received message is one copy. encode_canonical writes it field by field instead, in Google's order.

Errors

Decoding and encoding errors carry codes GIONG-E4001 to GIONG-E4008 (ErrorKind), each with a page in docs/errors/: truncated input, malformed varints, invalid tags, unbalanced groups, non-UTF-8 strings, nesting deeper than 100, malformed packed fields, messages over 2 GiB.

How it is checked

  • Google's protobuf conformance suite (conformance_test_runner from protobuf v36.2): every binary-format test passes, required and recommended, 1414 of 1414, for proto2 and proto3. JSON and text-format tests are skipped: giong-proto reads and writes the binary format only. Run it with giong-proto/conformance/run.sh.
  • Differential tests against prost (giong-proto/conformance): the same bytes into both; when both accept, prost must read giong-proto's canonical re-encoding as the same message; when only one accepts, the difference must be one of two documented ones (below). A seeded generator runs in the test suite, and the differential target in fuzz/ runs the same check under libFuzzer.
  • Unit tests for the wire format, a test of the message structs against prost for every kind of field, and the example's tests.

Where giong-proto follows Google's libraries and prost does not (the differential test allows exactly these):

  1. A known field arriving with the wrong wire type is kept as an unknown field; prost rejects the message (and for map fields skips the check and misreads what follows).
  2. A proto2 (closed) enum field holding a number the enum does not define keeps that number as an unknown field; prost stores it as the field's value.

Known gaps against Google's libraries: proto2 string fields are checked for UTF-8 (Google accepts invalid UTF-8 there unchecked; prost rejects it, as giong-proto does); editions (edition = "2023") and extensions are not supported; no JSON or text format.

What a view costs instead of allocations: nested messages inside repeated fields are parsed once at decode (to check them) and again when the iterator reaches them, so messages made mostly of small repeated sub-messages gain less than the others.

For agents

  • One way to read (XView::decode, then accessors) and one way to write (the X struct, then encode). Accessors never fail: all checking happens in decode.
  • Views borrow the input: keep the buffer alive as long as the view. To keep data longer, copy what you need (.to_string(), .to_vec()), or keep the bytes and decode again.
  • Match errors on err.kind() (giong_proto::ErrorKind), not on the message text.
